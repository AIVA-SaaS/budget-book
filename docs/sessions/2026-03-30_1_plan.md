### 문제 2: 거래 미생성 — 복합 원인
**BE 로직 점검**: `completeWithTransaction()` 코드 자체에 Transaction 생성+저장 코드 존재. 명확한 단일 버그 아님.

**발견된 문제점들:**
1. **BE 테스트 부재**: `completeWithTransaction`에 대한 테스트가 전혀 없음 → 실제 DB에서 동작 미검증
2. **FE 두 경로 혼재**: `createTransaction` 체크박스가 꺼지면 `CompletePlan` 호출 → 거래 생성 없이 상태만 COMPLETED 변경
3. **FE 에러 핸들링 미흡**: `catch (e)` 블록이 일반 에러메시지만 표시, 실제 원인 숨김
4. **폼 페이지 타이밍**: `context.pop()` 즉시 호출 → 비동기 API 결과 확인 불가, 에러 SnackBar도 안보임
5. **완료 후 TransactionBloc 미갱신**: 거래 목록 리로드 안함 → 새 거래가 표시 안됨
6. **완료 후 Wishlist 리로드 누락**: `_onCompletePlan`, `_onCompleteWithTransaction` 둘 다 wishlist 미갱신

**해결 방향**: 완료 처리 = 반드시 거래 등록으로 설계 변경
- `createTransaction` 체크박스 제거 → 완료 시 항상 `completeWithTransaction` 호출
- 거래 없이 상태만 변경하고 싶으면 "건너뛰기" 사용
- 폼 페이지에서 완료 결과 확인 후 pop (async 대기)
- 완료 후 TransactionBloc도 갱신

### 문제 3: 상태 이력 추적 없음 (BE + FE 신규)
- DB에 audit 테이블 없음 — `updated_at`만 존재
- 누가, 언제, 어떤 상태에서 어떤 상태로 변경했는지 추적 불가
- 완료 시 실제 금액 vs 계획 금액 차이 이력 없음

## 성능 설계
- **데이터 접근**: 이력 테이블은 `spending_plan_id` 인덱스로 조회. 계획당 이력 건수 최대 5~10건
- **예상 규모**: 월 20~50개 지출 계획 × 2~3회 상태 변경 = 월 100건 미만
- **리소스 제약**: 추가 쿼리 1회 (이력 조회). 목록 API에는 이력 미포함
- **설계 결정**: 별도 테이블로 이력 관리. 목록 성능 유지

## DB 스키마 설계

```sql
-- V41: 지출 계획 상태 변경 이력
CREATE TABLE spending_plan_status_history (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    spending_plan_id UUID NOT NULL REFERENCES spending_plans(id) ON DELETE CASCADE,
    from_status VARCHAR(20),  -- NULL for initial creation
    to_status VARCHAR(20) NOT NULL,
    changed_by UUID NOT NULL REFERENCES users(id),
    actual_amount BIGINT,         -- 완료 시 실제 금액
    linked_transaction_id UUID,   -- 완료 시 연결된 거래
    note TEXT,                    -- 변경 사유/메모
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT ck_status_history_to CHECK (to_status IN ('WISHLIST','PLANNED','COMPLETED','SKIPPED','OVERDUE')),
    CONSTRAINT ck_status_history_from CHECK (from_status IS NULL OR from_status IN ('WISHLIST','PLANNED','COMPLETED','SKIPPED','OVERDUE'))
);

CREATE INDEX idx_status_history_plan_id ON spending_plan_status_history(spending_plan_id);
CREATE INDEX idx_status_history_created_at ON spending_plan_status_history(created_at);
```

## API 변경

### 완료 처리 (변경 없음 — 기존 endpoint 활용)
```
PATCH /api/v1/spending-plans/{id}/complete-with-transaction
```
FE에서 항상 이 엔드포인트만 호출. `completePlan` 엔드포인트는 유지하되 FE에서 사용 안함.

### 이력 조회 (신규)
```
GET /api/v1/spending-plans/{id}/history
→ ApiResponse<List<StatusHistoryResponse>>
```

## 완료 처리 플로우 변경 (Before → After)

### Before
```
다이얼로그 → 체크박스 ON/OFF → CompleteWithTransaction 또는 CompletePlan
                                  (거래 생성)         (거래 없음, 상태만 변경)
```

### After
```
다이얼로그 → 항상 CompleteWithTransaction (거래 항상 생성)
           → description 편집 가능
           → 완료 성공 시 TransactionBloc 갱신
           → 이력 자동 기록
```
