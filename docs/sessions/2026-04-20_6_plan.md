# Phase 21 — 필터 시스템 전면 리팩터
> 날짜: 2026-04-20 | 회차: 6 | 상태: 검증완료/승인대기
> 전신: `2026-04-20_5_plan.md` (DEPRECATED, 범위 확대로 이 문서가 대체)

## 요청 내용 (누적)
사용자가 총 2회에 걸쳐 제시한 필터 시스템 문제들:

1. 현재 기간 필터 설정 시 바로 적용되는데 다른 필터들은 모두 다른 필터도 선택하고 적용해야 적용된다. 기간도 선택 후 다른 필터까지 선택한 뒤 적용하는게 맞을 것 같다.
2. 필터 내 결제수단, 카테고리 선택 부분이 거래에서 선택하는 UI와 완전 다른데 공통화에 맞게 적용되도록
3. 필터에서 카테고리 선택 시 상위 그룹도 선택할 수 있어야 하는데 지금은 1개의 하위 카테고리만 선택 가능하다.
4. 여러 개 선택할 수 있는 옵션도 있어야 하는데 그런 게 전혀 고려되지 않았다.
5. 예를 든 사례 외에도 공통 적용된 부분들이 존재하는데 따로 동작하는게 너무 많다. (= 파편화 일소)
6. 필터에서 공개 범위 미 적용
7. 필터에서 UI 깨짐

## 문제 진단 (7건)

### P1. 기간 필터 즉시 적용 (UX 비대칭)
- 위치: `frontend/lib/core/widgets/filters/unified_filter_bar.dart:244~284`
- "기간 변경" 프리셋 탭 → 외부 시트 `Navigator.pop(ctx)` + 즉시 `onFilterChanged(state.copyWith(dateFrom..., dateTo..., dateRangeLabel:...))`
- 다른 필터(카테고리/결제수단/포켓/금액/거래유형/공개범위)는 모두 시트 내부 `tempXxx` 로컬 변수 → 하단 "적용" 버튼 클릭 시 일괄 propagate
- 결과: 기간만 즉시 적용 → 사용자가 다른 필터 추가 선택하기 전에 네트워크 요청 발생, 시트 강제 종료, UX 일관성 깨짐

### P2. 카테고리 UI 패턴 파편화 (거래 폼 ≠ 필터)
- 거래 폼: `ItemSelectorField` (label+prefix icon+suffix arrow) → 탭 → `CategoryGroupSelectorSheet` (Dialog)
- 필터: `InputDecorator` (단순 텍스트, dropdown 아이콘) → 탭 → `CategoryGroupSelectorSheet` (showModalBottomSheet)
- 트리거 UI 와 sheet 호출 방식이 다름 (Dialog vs ModalBottomSheet)

### P3. 카테고리 그룹 선택 불가
- `CategoryGroupSelectorSheet` 의 그룹 헤더(line 399-476)는 `onTap: setState(() => _expandedGroupIds.add/remove)` — **expand/collapse 전용**, 그룹을 선택 대상으로 사용할 수 없음
- 필터 컨텍스트에서 "식비 그룹 전체"를 한 번에 고르지 못함

### P4. 다중 선택 UI 전혀 없음
- 모델은 이미 `Set<String>` 다중 구조:

  ```dart
  String? tempPaymentMethodId = state.paymentMethodIds.isNotEmpty ? state.paymentMethodIds.first : null;
  ```

## 구조적 수정 — 재발 방지 (필수 — 하네스 STRUCTURAL_FIX_REQUIRED)

### 배경
하네스 recurrence check 결과 `filter_propagation` 카테고리 3회 인시던트 누적 + 이번 건(visibility 미전달)은 **4회째 재발**. 패치 금지, 근본 설계 변경 필수.

### 설계 — 컴파일 타임 강제 (단순 체크리스트 금지)

#### S1. Repository 인터페이스에서 단수 필드 **삭제** (호환 오버로드 금지)
```dart
// ❌ 기존
Future<Either<Failure, PageResponse<Transaction>>> getTransactions({
  String? categoryId,
  String? paymentMethodId,
  String? pocketId,
  // visibility 없음 ← 근본 문제
});

// ✅ 신규 — 단수 필드 완전 제거 (컴파일 타임 마이그레이션 강제)
Future<Either<Failure, PageResponse<Transaction>>> getTransactions({
  Set<String> categoryIds = const {},
  Set<String> categoryGroupIds = const {},
  Set<String> paymentMethodIds = const {},
  Set<String> pocketIds = const {},
  String? visibility,  // 'ALL' | 'SHARED' | 'PRIVATE', null → 전체
  // 기타 기존 필드
});
```
- 단수 파라미터를 제공하지 않으므로 `categoryId:` 로 호출하는 모든 코드는 컴파일 실패 → 호출처 강제 마이그레이션
- 빈 Set 이 기본값 = "전체" 의미, nullable 제거로 nullable 체크 누락 방지

#### S2. Filter VO 단일 접근점 강제 — `TransactionFilter.toQueryParams()` 확장 함수 중앙화
```dart
extension TransactionFilterQueryParams on TransactionFilter {
  Map<String, dynamic> toQueryParams() => {
    if (year != null) 'year': year,
    if (month != null) 'month': month,
    if (type != null) 'type': type,
    if (categoryIds.isNotEmpty) 'categoryIds': categoryIds.toList(),
    if (categoryGroupIds.isNotEmpty) 'categoryGroupIds': categoryGroupIds.toList(),
    if (paymentMethodIds.isNotEmpty) 'paymentMethodIds': paymentMethodIds.toList(),
    if (pocketIds.isNotEmpty) 'pocketIds': pocketIds.toList(),
    if (visibility != null && visibility != 'ALL') 'visibility': visibility,
    if (dateFrom != null) 'dateFrom': dateFrom,
    if (dateTo != null) 'dateTo': dateTo,
    if (amountMin != null) 'amountMin': amountMin,
    if (amountMax != null) 'amountMax': amountMax,
    if (keyword != null && keyword!.isNotEmpty) 'keyword': keyword,
  };
}
```
- RemoteDataSource 는 이 확장 함수만 호출 → 신규 필터 추가 시 이 한 곳에만 추가하면 BE 전달 누락 0
- 기존 `if (categoryId != null) queryParams['categoryId'] = categoryId` 같은 인라인 직렬화 전면 제거

## 선택 sheet 아키텍처

### ItemSelectorSheet 확장
```dart
enum SelectionMode { single, multi }

class ItemSelectorSheet extends StatefulWidget {  // StatelessWidget → StatefulWidget
  final SelectionMode mode;
  final Set<String> initialSelectedIds;  // multi 모드
  final String? selectedId;              // single 모드 (기존)
  final void Function(Set<String> ids)? onApplyMulti;
  final ValueChanged<SelectorItem?>? onSelected;  // single
  // 기타 기존 필드
}
```
- multi 모드: 각 ListTile 좌측에 체크박스, 그룹 헤더에 "그룹 전체" 체크박스(그룹 내 아이템 일괄 토글), 하단 "전체 선택"/"해제" + "적용" 버튼
- single 모드: 기존 동작 유지 (즉시 Navigator.pop + onSelected)

### CategoryGroupSelectorSheet 확장
```dart

  final Set<String> initialGroupIds;

```
- `multiCategoryWithGroup` 모드:
  - 그룹 헤더 좌측에 **체크박스** — 그룹 단위 선택 (체크 시 그 그룹의 모든 카테고리 자동 포함, 해제 시 해제)
  - 카테고리 항목 좌측에도 체크박스
  - 하단 "적용" 시 `{categoryIds}, {groupIds}` 두 Set 반환
  - BE 에서 `groupIds` 받으면 CategoryRepository 로 펼쳐 `IN (categoryIds ∪ expandedFromGroups)` 적용
- 그룹과 개별 카테고리를 동시 선택 가능 (예: "식비 그룹 전체" + "교통 > 택시" 개별)

### displayLabel 전략
- 다중 선택 UI 에 적합한 표시 규칙:
  - 0개: "전체"
  - 1개: "카페·음식"
  - 2개 이상: "카페·음식 외 N개"
  - 그룹 포함: "식비 그룹 외 N개"
- 칩 영역은 기존 `_ActiveFilterChip` + `onRemove` 재사용 (각 칩 X 버튼이 해당 Set 초기화)

## 기간 적용 흐름 (P1)

## 성능 설계 (원칙 1.4)
### 데이터 접근
- 다중 카테고리: `WHERE category.id IN (:categoryIds)` — B-tree 인덱스 활용, 최대 N=50 개 이하로 제한 (UI 에서 그 이상 선택 불가하게 제약)
- 카테고리 그룹 펼치기: BE 한 번의 `SELECT id FROM categories WHERE group_id IN (:groupIds)` + 합집합 → 메인 쿼리는 여전히 IN 1회
- 쿼리 총 비용: 기존 단일 categoryId 대비 IN-clause 추가 비용 무시 가능 (인덱스 스캔)
### 예상 규모
- 커플당 카테고리 ~100개, 결제수단 ~20개, 포켓 ~10개 — 선택 상한 50 개 여유 충분
- 다중 필터 조합 시 카디널리티: SHARED+특정그룹+이번달 ~ 500~1000 행 범위
### 리소스
- Render 백엔드 512MB — IN-clause 50개 파라미터 직렬화는 수십 바이트, 무시 가능
- 클라이언트 메모리: Set<String> 4개 × 최대 50개 = 200 문자열, 무시 가능
### 설계 결정
- 그룹 ID 를 BE 에서 펼치는 이유: 클라이언트가 그룹→카테고리 매핑을 들고 있어도 BE가 정합성 보장하는 게 안전 (그룹에 카테고리 추가/삭제 동기화 불일치 방지)
- queryParams 직렬화: `categoryIds=a&categoryIds=b` multi-value 포맷 (Spring `List<UUID>` 자동 바인딩 대응)
