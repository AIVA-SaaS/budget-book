## 성능 설계

### 데이터 접근 패턴
- **대시보드**: summary + recentTransactions + budgetStatus 3개 API 병렬 호출 (Future.wait)
- **거래 검색**: DB 인덱스 활용 (year+month+type 복합 인덱스 기존 활용, keyword는 ILIKE + 부분 인덱스)
- **CSV 내보내기**: 스트리밍 응답 (메모리 제한 512MB 고려, 1만건 이상은 청크 처리)
- **전년 비교**: 2개 월 데이터 병렬 조회, 집계는 DB 레벨에서 수행

### 예상 규모
- 커플당 월 거래: 50~200건
- 카테고리: 20~50개
- 예산: 10~20개/월
- 포켓: 5~10개

### 리소스 제약
- Render free tier: 512MB RAM → JVM 384MB 제한 유지
- Supabase: Session Pooler 20 connections
- Redis (Upstash): 10K commands/day free tier
- Vercel: 100GB bandwidth/month

### 설계 결정
- 대시보드 데이터: 기존 API 재활용 (신규 집계 API 불필요)
- 검색: DB ILIKE (소규모 데이터에 충분, Full-text search는 오버엔지니어링)
- 오프라인: read-only 캐시 (write는 온라인 필수, conflict resolution 미구현)
- 모바일 OAuth: flutter_appauth (표준 방식, custom WebView 대비 보안 우위)
