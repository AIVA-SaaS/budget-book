## Transfer 테이블 설계

```sql
CREATE TABLE transfers (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    couple_id       UUID NOT NULL REFERENCES couples(id),
    author_id       UUID NOT NULL REFERENCES users(id),
    source_payment_method_id      UUID NOT NULL REFERENCES payment_methods(id),
    destination_payment_method_id UUID NOT NULL REFERENCES payment_methods(id),
    amount          BIGINT NOT NULL CHECK (amount > 0),
    description     VARCHAR(255),
    memo            TEXT,
    transfer_date   DATE NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMP NOT NULL DEFAULT NOW(),

    CONSTRAINT chk_different_methods CHECK (source_payment_method_id != destination_payment_method_id)
);

CREATE INDEX idx_transfers_couple_date ON transfers(couple_id, transfer_date);
CREATE INDEX idx_transfers_source ON transfers(source_payment_method_id);
CREATE INDEX idx_transfers_dest ON transfers(destination_payment_method_id);
```

### 장점 (vs Transaction 확장 방식)
| 리스크 | Transaction 확장 | 별도 Transfer 테이블 |
|--------|-----------------|-------------------|
| 기존 8+ 집계 쿼리 수정 | 필요 (누락 시 통계 오염) | **불필요** |
| 고아 거래 (한쪽만 삭제) | 발생 가능 | **불가능** |
| 금액 불일치 (한쪽만 수정) | 발생 가능 | **불가능** |
| IDOR 취약점 | transferGroupId 스푸핑 | **없음** (couple 소속 검증) |
| 예산/통계 오염 | 필터 누락 시 발생 | **원천 차단** |
| 기존 코드 영향 | 8+ 파일 수정 | **0개 파일 수정** |

## 이체 API 명세 (초안)

### POST /api/v1/transfers
```json
// Request
{
  "sourcePaymentMethodId": "uuid",
  "destinationPaymentMethodId": "uuid",
  "amount": 100000,
  "description": "신한->현금 ATM 출금",
  "transferDate": "2026-03-25",
  "memo": "optional"
}

// Response 201 Created
{
  "success": true,
  "data": {
    "id": "uuid",
    "coupleId": "uuid",
    "author": { "id": "uuid", "nickname": "..." },
    "sourcePaymentMethod": { "id": "uuid", "name": "신한은행", "type": "BANK" },
    "destinationPaymentMethod": { "id": "uuid", "name": "현금", "type": "CASH" },
    "amount": 100000,
    "description": "신한->현금 ATM 출금",
    "memo": null,
    "transferDate": "2026-03-25",
    "createdAt": "2026-03-25T10:00:00"
  }
}
```

### GET /api/v1/transfers?year={year}&month={month}
- 커플 소속 이체 목록 조회 (월별 필터)
- Response: `ApiResponse<List<TransferResponse>>`

### GET /api/v1/transfers/{id}
- 단건 조회. 커플 소속 검증 필수.

### PUT /api/v1/transfers/{id}
- 수정 가능 필드: amount, description, memo, transferDate, sourcePaymentMethodId, destinationPaymentMethodId
- 단일 레코드이므로 불일치 위험 없음

### DELETE /api/v1/transfers/{id}
- 204 No Content. 커플 소속 검증 필수.

## 성능 설계
- **데이터 접근**: 이체 CRUD는 단일 테이블 단일 레코드 (가장 단순한 패턴)
- **예상 규모**: 이체는 월 10~30건 수준. 성능 영향 무시 가능
- **쿼리**: couple_id + transfer_date 복합 인덱스로 월별 조회 최적화
- **리소스 제약**: 없음 (로컬 개발 + Supabase)
- **기존 영향**: 기존 Transaction 테이블/쿼리 **수정 없음** -> 리그레션 위험 제로

## 보안 설계 (감사 결과 반영)

| 보안 항목 | 대응 |
|----------|------|
| 커플 소속 검증 (IDOR 방지) | 모든 CRUD에서 `coupleId` 일치 확인 (OwnershipValidator 패턴) |
| 입력 검증 | amount > 0, sourceId != destId (DB CHECK + 서비스 레이어) |
| 금액 제한 | @Min(1) @Max(999_999_999) — 기존 Transaction과 동일 |
| @Transactional | 모든 쓰기 작업에 적용 |
| DTO 분리 | Request/Response DTO 명확 분리, 내부 필드 노출 차단 |
| Rate limiting | 기존 글로벌 rate limit 적용 (추가 불필요) |
