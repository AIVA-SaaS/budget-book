### A-1. DB 마이그레이션 (V49)
```sql
-- 피드백 투표 테이블
CREATE TABLE feedback_votes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    post_id UUID NOT NULL REFERENCES feedback_posts(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
```

**투표 로직:**
```kotlin
fun toggleVote(postId: UUID, userId: UUID): Boolean {
    val existing = voteRepo.findByPostIdAndUserId(postId, userId)
    if (existing != null) {
        voteRepo.delete(existing)
        postRepo.decrementVoteCount(postId)
        return false  // 투표 취소
    } else {
        voteRepo.save(FeedbackVote(postId = postId, userId = userId))
        postRepo.incrementVoteCount(postId)
        return true  // 투표 추가
    }
}
```

## Sprint C: 스마트 분석 (패턴 학습 + 예산 조정 + 통계 인사이트)

> 외부 AI API 없이, 서버 내 통계/규칙 기반으로 구현

### 현재 상태
- AI 분류: 패턴매칭(DB 기반 getSuggestions) 동작 중, Claude API는 비활성
- AI 인사이트: API 비활성 시 빈 배열 반환 (실질적 미동작)
- 기존 AiClassificationService의 패턴매칭은 description 유사도 기반

### C-1. DB 마이그레이션 (V50)
```sql
-- 카테고리 분류 학습 테이블
CREATE TABLE category_patterns (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    couple_id UUID NOT NULL REFERENCES couples(id) ON DELETE CASCADE,
    keyword VARCHAR(100) NOT NULL,
    category_id UUID NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
    frequency INT NOT NULL DEFAULT 1,
    last_used_at TIMESTAMP NOT NULL DEFAULT NOW(),
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_category_pattern UNIQUE (couple_id, keyword, category_id)
);
CREATE INDEX idx_category_patterns_couple_keyword ON category_patterns(couple_id, keyword);
```
- 담당: Contract | 난이도: S

### C-2. BE: 패턴 학습 서비스
**신규 파일:**
- `PatternLearningService.kt` — 분류 패턴 학습/조회
- `CategoryPattern.kt` (엔티티)
- `CategoryPatternRepository.kt`
- `SmartAnalysisService.kt` — 통계 기반 인사이트 생성
- `SmartAnalysisController.kt` — 신규 엔드포인트

**학습 로직:**
```
거래 생성/수정 시:
  1. description에서 키워드 추출 (공백 split, 2글자 이상)
  2. (couple_id, keyword, category_id) 조합으로 frequency +1 (UPSERT)
  
분류 제안 시:
  1. description에서 키워드 추출
  2. category_patterns에서 couple_id + keywords 매칭 → frequency 높은 순 정렬
  3. 기존 getSuggestions() 결과와 병합, 학습 결과 우선
```

**엔드포인트:**
- `GET /api/v1/smart/classify?description=...` — 학습 기반 분류 제안 (기존 /ai/classify 대체)
- `GET /api/v1/smart/insights?year=&month=` — 통계 기반 인사이트
- `GET /api/v1/smart/budget-suggestions` — 예산 조정 제안

- 담당: BE | 난이도: M

### C-3. BE: 통계 기반 인사이트 엔진
**SmartAnalysisService — 규칙 기반 인사이트 생성:**

| 규칙 | 조건 | 인사이트 유형 | 예시 |
|------|------|-------------|------|
| 전월 대비 증가 | 카테고리 지출 >20% 증가 | SPENDING_CHANGE | "식비가 전월 대비 32% 증가 (28만→37만)" |
| 예산 초과 경고 | 예산 대비 >80% 사용 (월 중반) | BUDGET_WARNING | "교통비 예산 80% 소진, 남은 기간 주의" |
| 주말 패턴 | 주말 지출 > 평일 1.5배 | PATTERN | "주말 평균 지출이 평일의 1.8배" |
| 절약 팁 | 특정 카테고리 매달 일정액 이상 | TIP | "카페 월 평균 5.2만원, 줄이면 연 62만원 절약" |
| 긍정 트렌드 | 3개월 연속 지출 감소 | POSITIVE | "3개월 연속 총 지출 감소 추세!" |
| 예산 조정 제안 | 실 지출 vs 예산 >30% 차이 (3개월) | BUDGET_ADJUST | "식비 실제 평균 42만, 예산 30만 → 조정 제안" |

**데이터 소스:** 기존 TransactionRepository + BudgetRepository + StatisticsService 활용
**캐싱:** Redis TTL 1일 (매일 1회 계산)

- 담당: BE | 난이도: M

## 성능 설계

| 항목 | 설계 |
|------|------|
| 투표 토글 | vote_count 캐시 컬럼 → COUNT 쿼리 없음, O(1) |
| 공개 보드 | feedback_posts idx 활용, 페이징 20건 |
| 월별 트렌드 | 기존 월별 통계 API 6회 호출 또는 집계 쿼리 1회 |
| 패턴 학습 | keyword 인덱스, couple당 수백 건 이내 |
| 인사이트 생성 | 집계 쿼리 5~6개, Redis 캐시 1일 → 반복 조회 무부하 |
| 예산 제안 | 3개월 집계 → 쿼리 1회, 예산 비교 → 메모리 내 |
| NAS 제약 | 외부 API 호출 0, 순수 DB 집계만 → 메모리 영향 최소 |

## 검증 계획
- [ ] BE 테스트 통과 (`./gradlew test`)
- [ ] FE 분석+테스트+빌드 (`flutter analyze && flutter test && flutter build web`)
- [ ] BE↔FE↔Spec 일치 확인
- [ ] 성능 설계대로 구현 확인
- [ ] Root Cause Prevention 체크
  - P1: 투표 상태 서버 기준 (optimistic update 후 서버 응답으로 보정)
  - P2: vote_count 캐시 ↔ 실제 COUNT 불일치 방지 (트리거 or 서비스 레벨)
  - P4: 공개 보드 진입점이 명확한지, 투표 버튼 발견성
- [ ] 유저 플로우 시뮬레이션
  - 피드백 작성 → 공개 보드에 노출 → 다른 사용자 투표 → 카운트 증가
  - 홈 위젯 설정 변경 → 대시보드 반영 → 앱 재시작 후 유지
  - 거래 입력 → 스마트 분류 제안 → 선택 → 다음 입력 시 학습 반영
  - 인사이트 조회 → 통계 기반 분석 → 예산 조정 제안 확인

## 기획 검증 결과
- Sprint A~C 파일 영역 분리 확인 → 병렬 진행 가능
