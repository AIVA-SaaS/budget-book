## 2. 실측 현황 — "3회 공통화했는데 재발"의 정량 실체

### 2.1 공통 컴포넌트는 만들어졌고, **채택률이 평균 10.2%** 다

정의는 1개인데 **경쟁 경로가 살아 있다.** 주석 제외 코드 라인만 셌다.

- `EntityTileRow` 채택 6 / 경쟁 `ListTile` 계열 86 → **7%**
- `BbColors`(의미색) 32 / 하드코딩 색 470 → **6%**
- `BbWideButton` 8 / `FilledButton`·`ElevatedButton`·`OutlinedButton` 81 → **9%**
- `OneLineLabel` 7 / `overflow: TextOverflow.ellipsis` 49 → **12%**
- `BbCardTile` 11 / 생 `Card` 65 → **14%**
- `EmptyStateWidget` 14 / 자체 빈 상태 83 → **14%**
- `ItemSelectorField` 18 / `InputDecorator`·`DropdownButtonFormField` 11 → **62%**
- `BbCardGap`/`bbCardItems`(2026-08-26 신설) 21 / 0 → **100%**

합계 채택 96 · 경쟁 845 → **10.2%** `[추론: 위 합]`.

**★이것이 재발의 기제다.** `domains/12-ui-scaling.md` 가 이미 경고한 문장이 그대로 실현됐다 —
"토큰을 **추가**하는 것만으로는 안 고쳐진다. 같은 자리의 리터럴이 남아 있으면 그게 **경쟁 경로**이고 축이 3개에서 4개로 늘 뿐이다. 완료 기준은 **'경로를 추가했다'가 아니라 '경쟁 경로를 0개로 만들었다'**".

3회 회차가 **정의를 만들고 시범 범위만 배선**했고, 나머지를 총량 래칫에 맡겼다. 래칫은 "늘지만 않으면" 통과하므로 **한 경로만 이관하고 나머지를 남기는 패턴을 영구히 통과시킨다.**

### 2.2 시트 셸(shell) 자체가 공통화되지 않았다

같은 역할의 폼 시트 5종(`payment_method` 430줄 · `pocket` 362 · `category` 321 · `category_group` 287 · `pocket_transfer` 228)을 구성요소로 대조하면 **전 시트 공통 요소가 7종**인데 **각각 독립 구현**이다.

공통 7종: 드래그 핸들 · `TextFormField` · `FilledButton` · `Form(key:)` · `GlobalKey<FormState>` · `validator:` · `viewInsets` 처리.

그 값이 **파일마다 따로 하드코딩**돼 있다 — 지금은 우연히 같지만 소스가 5개다.

- 드래그 핸들 **`40x4` 가 5곳**
- 시트 하단 **`viewInsets.bottom + 24` 가 5곳** — 리터럴 24 가 5개 소스
- **`FilledButton` + `styleFrom` 이 5곳** — 버튼 계약이 5개
- **`BorderRadius.circular(2)` 가 5곳**(핸들), 그 외 `8`·`20` 산재

⚠ **9차 회차의 세로 간격 이관이 이걸 전부 놓쳤다** — 이관 대상이 `SizedBox(height:)` 1경로였고 `viewInsets.bottom + 24` 는 `EdgeInsets.only(bottom:)` 형태였다.

### 2.3 선택 시트 3종이 같은 역할인데 별개다

`item_selector_sheet` **25KB** · `category_group_selector_sheet` **37KB** · `hierarchical_selector_sheet` **13KB** = 합 **75KB**. 셋 다 "목록에서 하나 고르기"다. `calendar_picker_dialog` · `month_year_picker_dialog` · `color_picker` · `icon_picker` · `period_selector` 도 같은 계열의 별개 구현이다(합 8파일 · 약 133KB).

### 2.4 프레임워크가 소유권을 쥔 자리가 반복된다 (7차 교훈 재발)

같은 패턴을 **3번** 겪었다 — `ListTile`(7차, 높이) · `Card`(9차, 블록 간격) · **`InputDecorator`(9차 미해결, 필드 높이)**.

`ItemSelectorField` 실측 `[측정 2026-08-27, test/measure_form_gap_test.dart]`:

- 필드 상자 높이 **48.00 / 48.00 / 48.00** (390·768·960dp) — 폭에 **전혀 반응하지 않는다**
- 내부 아이콘 슬롯 **40.0 → 45.3 → 48.0** 으로 커지며 테마 `contentPadding`(`lg` 8.00→12.00) 증가분을 **흡수**한다
- 결과: 상자top→텍스트top 이 **14.50 → 14.00 → 13.50** — 화면이 넓어질수록 여백이 **줄어드는 역행**
- 필드 **사이**는 정상(`xxl` 15.30 / 21.47 / 24.00)

판정 규칙 `[측정]`: **상자 높이가 3폭에서 같으면 프레임워크가 소유한 것**이다. 여백 토큰을 넣기 전에 이걸 먼저 재야 한다.

### 2.5 BE 도 같은 병이다 — 공통 상위 계약이 **하나도 없다**

Kotlin `src/main` **207파일**. Controller 27 · Service 36 · Repository 30 · Request 56 · Response 68.

- **`BaseEntity` 0 · `BaseController` 0 · `BaseService` 0 · `BaseRepository` 0**
- `@Entity` **29개** 중 공통 상위를 상속하는 것 **0개**
- Service: `interface …Service` 선언 **1** vs `class …Service` 선언 **35** → **인터페이스 기반 계약이 사실상 없다**(요구 4 정면 위반)
- 같은 항목이 파일마다 반복 선언: `coupleId` **54파일** · `visibility` **45** · `createdAt` **40** · `displayOrder` **14**
- 공통화된 것은 `ApiResponse` **30파일** 하나뿐(`CLAUDE.md` 규칙으로 강제돼 있다 — **강제된 것만 지켜졌다**는 증거)

## 3. 근본 원인 가설 (다음 세션이 반증할 대상)

`[추론]` — 세 겹이고, 각각 반증 수단을 병기한다.

1. **완료 기준이 "정의를 만들었다"였고 "경쟁 경로 0"이 아니었다.** 래칫은 총량만 보므로 부분 이관을 영구 통과시킨다.
   반증 수단: 3회 회차의 완료 기준 문구를 원문으로 꺼내 "경쟁 경로 0"이 수용 기준에 있었는지 확인.
2. **강제가 없는 공통화는 지켜지지 않는다.** 유일하게 지켜진 `ApiResponse`(30파일)는 `CLAUDE.md` 에 규칙으로 박혀 있고, 지켜지지 않은 7종은 문서·리뷰에만 있었다.
   반증 수단: 각 공통 컴포넌트에 대응하는 **차단 게이트 존재 여부**를 전수 확인(현재 `entity_tile_api_guard_test` 등 일부만 존재).
3. **커스터마이징 요구가 경쟁 경로를 정당화했다.** 공통 위젯이 필요한 변형을 못 받아주면 호출부가 프레임워크 위젯으로 되돌아간다.
   반증 수단: 경쟁 경로 845건을 표본 추출해 "공통 위젯으로 표현 불가한 변형이었나 / 그냥 안 쓴 것인가"를 분류.

**요구 2가 지목한 "인터페이스 형태로 확장"이 3번의 답이다** — 값 타입 슬롯(8차에 `EntityProgress`·`EntityOverflowMenu` 로 이미 검증된 관용구)으로 확장을 열되, 임의 위젯을 끼우는 경로는 막는다.

## 4. 다음 세션 착수 절차 (이 순서를 지킨다)

### Step 0 — 게이트·모드 정리

- **측정 모드 해제 확인**: 2026-08-27 현재 `fix 실패 2회 누적`으로 Edit/Write 가 차단돼 있다(`check-fix-mode.sh`). 사용자가 reset 키워드("잘 됨/통과/완료/해결됨")를 보내지 않았다면 **먼저 해제를 요청**한다.
- **하네스 audit 재감사**: `bash ~/.claude/harness/scripts/pre-change-audit.sh frontend "ui_pattern"` — 2026-08-27 교훈 유입으로 `ui_pattern` **16건**이 되어 승인이 자동 무효화됐다. 기획서에 구조적 수정안을 넣어야 게이트가 열린다.

### Step 1 — 전수 인벤토리 (Workflow 팬아웃)

"동일한데 별도 적용된 부분"을 **표본이 아니라 전수**로 만든다. 축을 병렬로 나눈다.

- FE-A 목록/타일 · FE-B 카드/블록 · FE-C 폼 셸 · FE-D 선택 시트/피커 · FE-E 버튼/액션 ·
  FE-F 빈 상태/로딩/에러 · FE-G 배지/칩 · FE-H 색·타이포·아이콘 · FE-I 여백 5경로 잔존 275건
- BE-A 엔티티 공통 필드 · BE-B Service 계약 · BE-C Controller·예외·응답 · BE-D Repository 쿼리 관용구

산출물은 **역할 → (정본 후보, 경쟁 경로 전 목록, 변형 요구 목록)** 이다. 표본 금지 — 전수여야 "일부만 적용" 이 불가능해진다.

### Step 2 — 총괄 검토(critic) → 재분석 루프

인벤토리마다 독립 검증자가 "누락된 축 / 잘못 묶은 역할 / 변형 요구 오독"을 찾는다. 미흡하면 Step 1 재실행.

### Step 3 — 재설계: 계약 + 확장 인터페이스

역할별로 **정본 1개 + 값 타입 확장 슬롯**을 설계한다. 임의 위젯 주입 경로는 노출하지 않는다(8차 `entity_tile_api_guard_test` 가 이미 강제하는 관용구).

BE 는 `BaseEntity`(coupleId·createdAt·updatedAt·visibility) · `…Service` 인터페이스 + 구현 분리 · 공통 예외·응답 계약.

### Step 4 — 강제 장치를 **설계와 동시에** 만든다 (핵심)

문서·리뷰로는 3회 실패했다. 각 정본에 대해:

- **경쟁 경로 0 게이트** — 역할별 경쟁 패턴이 도달 가능 파일에서 0건임을 테스트가 단정. 총량 래칫과 **별도**다
- **기획서 경로 목록 = 가드 검사 목록**을 같은 상수에서 읽게 만든다(9차 실패의 직접 처방 — 기획서는 5경로, 가드는 1경로였다)
- **소유권 판정 가드** — 상자 높이가 3폭에서 같으면 실패(프레임워크 소유 탐지)
- **채택률 게이트** — 역할별 채택률이 내려가면 실패(현재 10.2% 를 기준선으로 박고 래칫)

### Step 5 — 단계 이행 + 검증

역할 하나씩 이관하고 **매 단계 대조군**(변경 전 코드에서 새 가드가 실패하는지)을 확인한다. 통과하는 대조군은 축이나 지표가 틀린 것이다(9차 R1 이 실제로 그랬다).

로컬 CI 전부 → PR → 배포 → 라이브 검증. `phase{N}-step{M}` 태그를 안정 SHA 마다 붙인다.

## 7. 미해결 사항 (확인 주체·수단 병기)
