# 행 안·행 사이 **위아래 균형** — 세로 리듬 6차 (전수 검사)

> 회차: 2026-08-24 #3 · 선행 4차(PR #311 카드) · 5차(PR #313 슬롯)

## 1. 전수 계측 결과 `[측정]` (2026-08-24)

계측기: `frontend/test/measure_row_balance_test.dart`(신규) ·
`measure_budget_gap_test.dart` · `measure_global_gap_test.dart`.
지표 3종을 **동시에** 본다 — 행 사이 / **행 안 위·아래**(균형 지표) / 선행 위젯 내부.

### ① 거래 탭 — 선행 위젯이 행 박스를 **넘친다**

- 타일 박스 **45.0** @390, 선행 Column(아바타 32 + `xs` 4 + 캡션 14) = **50**
- 타일 상단 → 아바타 = **−1.5** · 결제수단 글자 → 타일 하단 = **−4.5**
- 결과 **행 사이 = −6.0** (겹친다) → "아래 글자가 붙는다"
- @960 은 박스 53.0 으로 딱 0.0/0.0

### ② 분석>예산 — 여백이 아니라 **부제목 3줄 랩**이 행을 키운다

- 행 박스 **93.0** @390 · 위 여백 **10.0** / 아래 여백 **10.0**(대칭·정상)
- 부제목 `250,000원 / 400,000원 (62.5%)` 이 폭 **145.6dp** 안에서 **3줄 = 45.0dp**
  → 행 높이의 **48%**. @430 2줄(30.0) · @768 1줄(15.0)
- 즉 "여백이 엄청 많다"의 지배 변수는 **랩**이고, 그 폭을 좁히는 것은
  trailing(금액 116dp + 메뉴 44dp)이다

### ③ 자산 탭 결제수단 · 카테고리 탭 — 위/아래가 **3배 비대칭**

- 칩+액션 행: 박스 69.2 · 위 **12.0** / 아래 **4.0** · 사이 16.0
- 칩만 행: 박스 65.2 · 위 10.0 / 아래 8.0 · 사이 18.0
- 카테고리 탭도 `EntityTileRow` + `actions.menu` + `reorderIndex` → 같은 경로
  (`category_list_tile.dart:36`)

## 2. 진단 — 원인 2개는 **내가 만든 회귀**다

### 회귀 A (5차 PR #313) — 액션 행의 세로 여백 0

`entity_tile_row.dart` 에 `hasTallSlot ? 0 : space.xs` 를 넣었다. 44dp 터치 슬롯이 든 행은
여백이 0 이 되어 **아래가 4.0** 으로 붙는다(위는 슬롯 잉여로 12.0). 증상 ③의 직접 원인이고
**자산 탭·카테고리 탭·자산 현황 전부**가 이 경로다.

### 회귀 B (3차 PR #308) — `minTileHeight` 가 선행 위젯보다 낮다

3차에서 `ListTileThemeData(minVerticalPadding: 10, minTileHeight: 34)` 를 넣어 2줄 타일
높이가 **72(M3 기본) → 45** 로 내려갔다. 거래 탭의 선행 Column 은 **50** 이라 이제 넘친다.
증상 ①의 직접 원인이다 `[측정]`. 3차 당시 지표가 텍스트↔텍스트였기 때문에 **선행 위젯
높이를 계측 축에 넣지 않았다.**

### 구조적 원인 (회귀가 반복되는 이유)

```
행 사이 = 행 박스 − 행 잉크
행 박스 = max(선행, 액션 슬롯, 텍스트 블록) + 위 여백 + 아래 여백
```

여백·슬롯·선행·랩이 **각각 다른 파일에서** 박스를 정한다. 지금까지 회차마다 한 항씩
건드렸고, 그래서 한 표면을 맞추면 다른 표면이 깨졌다(3차 → ①, 5차 → ③).

## 3. 처방 — 행 리듬 단일 소유자 `BbRow`

**규칙(불변식)**

1. **위 여백 = 아래 여백** (대칭) — 사용자 요구의 핵심
2. `행 박스 = max(행 잉크, 선행, 터치 슬롯 44) + 2 × padV`, `padV = listRowPadV`(10 / 12.5)
   → 선행이 커도 **넘치지 않고 박스가 커진다**(① 해소), 슬롯이 커도 **여백을 0 으로
   깎지 않는다**(③ 해소)
3. **행 사이 = 2 × padV = 20.0 / 25.0**. 예외는 1줄 + 44슬롯 행뿐(박스가 44 에 묶여 24.0)
   — 이 값은 가드가 명시적으로 소유한다
4. 랩은 리듬 문제가 아니라 **폭 문제**다 → ②는 부제목 `maxLines`·문자열·trailing 폭으로
   따로 다룬다(같은 회차, 다른 축으로 분리 기록)

**적용 순서**(회귀 위험 순)

1. `EntityTileRow` — `hasTallSlot ? 0 : space.xs` 를 **대칭 규칙으로 교체**(회귀 A 원복)
2. `app_theme.dart` `minTileHeight` — 선행 위젯 최대 높이(50)를 하한에 반영하거나,
   거래 타일의 선행을 `subtitle` 로 이관해 선행 높이를 32 로 낮춘다(회귀 B, 택1)
3. `account_balance_card` 자산 현황 = **자산 탭과 같은 위젯 계약**으로 통일(사용자 지시)
4. 예산 부제목 랩 — 폭 축 별건

## 7. 구현 결과 (2026-08-24, 같은 회차 · 승인 후)

### 7-1. §5 미해결 2건은 **새로 확인한 중복**으로 판정이 갈렸다 `[측정]`

- §5-1(회귀 B 택1) → **(a) 선행 캡션 삭제**. 결제수단명이 **선행 Column 과 부제목 두 곳**에
  있었다(`transaction_list_tile.dart` 선행 87행 · 부제목 200행). 그래서 "거래 목록 시각이
  바뀐다"는 우려가 사라졌고 `minTileHeight` 상향(모든 2줄 행 +5dp)도 필요 없어졌다 —
  사전 판정 기준("선행 높이가 32 로 내려가면 건드리지 않는다")대로 그대로 뒀다.
- §5-2(예산 랩) → **부제목의 분모 삭제**. `400,000원` 은 같은 행 trailing 에 이미 굵게
  있었다. 정보 손실 0 이라 사용자 판단 없이 진행했다(되돌리려면 문자열에 분모를 다시 넣는다 —
  `OneLineLabel` 이 1줄은 계속 보장한다).

### 7-2. 처방은 여백이 아니라 **구조**로 갔다 `[측정]`

`hasTallSlot ? 0` 은 슬롯 44 가 제목 행 **안**에 있다는 전제를 그대로 두고 여백만 깎은
처방이었다. 슬롯을 세로 흐름 밖(텍스트 블록의 형제)으로 빼면 슬랙이 Row 의 center 정렬로
위아래 균등하게 나뉜다 → 여백은 조건 없이 대칭(`xs`). 폭 계산은 항등식으로 불변임을
소스에 증명으로 남겼다(이중 차감 제거).

### 7-3. 계측 (변경 후 / 대조군)

- 변경 후: 칩 행 위 10.0 / 아래 8.0 · 사이 **18.0** @390 (칠해진 표면 기준 4.0 / 4.0),
  @960 12.5 / 8.0 · 사이 20.5 · 1줄+슬롯 행 6.0 / 6.0 · 사이 24.0 · 예산 항목 잉크높이
  93.0 → **43.0** · 사이 20.0 @375
- 대조군(변경 전 코드 + 새 가드): **5건 실패** — 칩+액션 행 위 6.0 / 아래 0.0(@390·@960),
  거래 타일 @390, 소스 봉인 2건. 가드가 회귀를 실제로 잡는다.

### 7-4. 새로 드러난 것 — `[미확인]` 아니라 `[측정]`, 그러나 **다른 축**

자산 현황 **그룹 경계 67.0dp**. 분해하면 그룹 박스 20(4차 승인값) + 그룹 헤더 잉크 +
44 슬롯이 만드는 행 슬랙 12 의 합이다. 행 축이 아니라 **그룹 축**이고, 줄이려면 그룹
박스(테두리 + 이중 padding)를 자산 탭처럼 없애야 한다 → 시각이 바뀌므로 사용자 결정 사항.
이번 회차 범위 밖으로 남긴다(§4 수용 기준 E 는 **행 계약 동일**이고 그건 충족됐다).

### 7-5. 가드 사고 4건 (하네스 등록 대상)

1. 봉인 테스트가 **주석 문구로 통과**했다 — 폐기한 표현을 주석에 인용했더니 초록이었다.
   소스 스캔은 주석을 제거하고 봐야 한다.
2. `find.byWidget` 은 위젯 **동일성**으로 찾는다 — `const` 로 canonical 화된 두 행이 한 행으로
   합쳐져 잉크가 두 행을 덮었다(아래 −74.0). 픽스처는 행마다 값을 달리한다.
3. `of: find.byType(InkWell)` 은 **모든 행**을 잡아 여백을 2배로 센다 → `.first`.
4. 아바타는 `CircleAvatar` 가 아니라 `Container(decoration:)` 이라 텍스트만 재면 원의 위쪽
   8.5dp 를 놓친다 → **대칭인 행이 12.5 vs 8.0 으로 오독**된다. 균형 축은 칠해진 표면으로.
