# 7차 — 예산 항목 행 간 높이 동일성 (2026-08-26)

> 승인: 2026-08-26 사용자 "두건 진행"
> 발단: 6차 라이브 검증 **3번 실패**(항목 82). 1·2 는 통과했다.

## 0. 요구 (사용자 문장 그대로)

> "3번은 의도와 다르게 됐다. **예산 간의 위 아래 항목 높이도 자산처럼 일치** 시키고 싶었던 건데 잘못 이해한 것 같다."

★명사는 **높이**이고 술어는 **일치**다. "줄여라"가 아니다. 6차는 이 문장을 **축소**로 읽었다.

## 1. 원인

### 1-1. 요구 오독 — 축을 잘못 골랐다

- 6차가 달성한 것 `[측정]`: 예산 항목 잉크높이 **93.0 → 43.0**(부제목 분모 중복 제거)
- 사용자가 원한 것: **항목 A 와 항목 B 의 높이가 서로 같을 것**
- 두 축은 독립이다. 높이를 줄여도 항목마다 다르면 요구는 미충족이다.

### 1-2. 구조 — 프레임워크가 높이를 소유한다

- `[측정: 코드]` `lib/features/budget/presentation/pages/budget_list_page.dart:743`
  `_buildBudgetTile` 이 **`ListTile`** 을 반환한다. `ListTile` 높이는 콘텐츠와 밀도가 정한다.
- `[측정: 코드]` 같은 함수의 `subtitle` 은
  `Column(SizedBox(4), _buildBudgetProgressBar(...), SizedBox(4), _buildBudgetSubtitleText(...))` 다.
- `[측정: 코드]` `_buildBudgetProgressBar` 는 **`budgetAmount <= 0` 이면 `SizedBox.shrink()`** 를 돌려준다
  (같은 파일 §`_buildBudgetProgressBar` 초입). → **바가 있는 항목과 없는 항목의 subtitle 높이가 다르다**
  → `ListTile` 높이가 갈린다. 이것이 "위아래 항목 높이가 다르다"의 직접 원인이다.

### 1-3. 대조 — 통과한 표면은 앱이 높이를 소유한다

- `[측정: 코드]` 6차에서 통과 판정을 받은 자산·카테고리는 `EntityTileRow` 를 쓴다
  (`lib/features/settings/presentation/pages/asset_management_page.dart`,
  `lib/features/category/presentation/widgets/category_list_tile.dart`).
- `[측정]` 그 계약은 6차에 세운 **`박스 = max(잉크 + 2 × xs, 슬롯 44)`** 다 — 슬롯을 세로 흐름 **밖**에 두어
  박스 높이가 잉크와 무관하게 하한을 갖는다.
- ★통과/실패가 갈린 지점이 정확히 **높이 소유권**이다. 사용자가 "자산처럼"이라고 말한 것이 바로 이 계약이다.

### 1-4. 가드 공백 — 축이 없었다

- `[측정: 코드]` `test/core/widgets/row_balance_guard_test.dart` 의 판정은
  `expect(top, closeTo(bottom, kBalanceTolerance))` = **한 행 안의 위/아래 대칭**이다.
- 행 **간** 높이를 비교하는 단언이 없다. 그래서 20/20 초록인 채로 이 결함이 배포됐다.

### 1-5. ★교훈 자체의 구멍 (가장 중요)

- `[측정]` 2026-08-24 `lessons-learned.jsonl` 교훈: **"'여백이 없다/많다' 회신은 축을 셋으로 갈라서 잰다:
  행 사이 · 행 안 위/아래(균형) · 랩(폭)"**
- **그 3축에 '행 간 높이 동일성'이 없다.** 교훈이 축을 빠뜨렸으니 계측기도 가드도 빠뜨렸다.
- `[측정]` 더구나 같은 교훈의 "놓친 위치"에 `budget_list_page.dart` 가 **이미 적혀 있었다**
  ("부제목의 예산 총액이 trailing 금액과 중복 — '여백이 많다'의 지배 변수가 여백이 아니라 랩이었다").
  같은 파일에서 **다른 축으로** 다시 샌 것이다.
- → 교훈을 **4축으로 보강**하는 것이 이번 회차의 재발 방지 본체다.

## 2. 착수 전 계측 (처방보다 먼저)

기존 계측기에 축을 더하거나 신설한다 — **4축 동시 출력**:

1. 행 사이(인접 행 top-bottom)
2. 행 안 위/아래 균형(칠해진 표면 기준 — 2026-08-24 교훈)
3. 랩(제목·부제목 줄 수)
4. **행 간 높이 동일성(신설)** — 같은 리스트 모든 행 높이의 최대-최소 차

- 대상 표면: 분석>예산 목록 · 자산(통과 대조군) · 카테고리(통과 대조군)
- `[측정]` 지배 변수를 수치로 고른 뒤 처방을 확정한다(2026-08-21 교훈: 지표를 먼저 고른다)
- ★픽스처는 **행마다 값을 달리한다**(`const` canonical 화 시 `find.byWidget` 이 두 행을 하나로 본다 — 2026-08-24 함정)
- ★**예산액 0 인 항목을 픽스처에 반드시 포함**한다. 그 케이스가 §1-2 의 분기를 타는 유일한 경로다.

### 사전 판정 기준

- 4축 중 **행 간 높이 차가 지배 변수**로 확인되면 §3 대로 진행
- 만약 높이 차가 허용오차 안인데 사용자가 다르게 본다면 지배 변수는 **다른 축**이다 →
  계측 결과를 그대로 보고하고 처방을 다시 고른다(추측으로 넘어가지 않는다)

## 3. 처방 — 구조적 수정 (게이트 요구)

`ui_pattern` 이 STRUCTURAL_FIX_REQUIRED 이므로 **패치 불허**. 높이 소유권 자체를 옮긴다.

- **S1 — 높이 소유권을 앱으로**: 예산 타일 `ListTile` → **`EntityTileRow` 이관**.
  이건 대기열의 "`ListTile` 87건/39파일 → `EntityTileRow` 이관(프레임워크가 높이를 소유하는 구조 해소)"
  의 **예산 화면 인스턴스**다. 개별 여백 조정이 아니다.
- **S2 — 조건부 렌더가 높이를 가르지 못하게**: 프로그레스바 자리를 **항상 예약**한다
  (`budgetAmount <= 0` 이어도 같은 높이의 자리를 유지). 값이 없다는 표현은 **높이가 아닌 수단**으로 한다.
- **S3 — 소스 봉인**: `budget_list_page.dart` 에 `ListTile(` 생성자가 없다. **주석 제거 후 스캔**
  (2026-08-24 교훈 — 주석 문구로 만족되는 봉인은 봉인이 아니다).

★요청이 한 축이면 한 축만 바꾼다(2026-08-21 교훈). 이번 회차에서 **좌우 여백·색·테두리는 건드리지 않는다** — 그때 전량 되돌림(PR #303 → #305)의 원인이 그것이었다.
