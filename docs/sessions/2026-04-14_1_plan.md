# Phase 18: 필터/금액/인사이트 정합성 수정
> 날짜: 2026-04-14 | 회차: 1 | 상태: 기획

## 요청 내용
사용자 보고 4가지 이슈:
1. AI 인사이트 클릭 시 잘못된 페이지(예산 관리)로 이동 — 카테고리별 사용 내역으로 이동해야 함
2. 필터 적용 시 합계 금액 불일치 — 필터된 거래만의 합계가 아닌 전체 합계가 표시됨
3. 필터 & 조회가 정상 작동하지 않음 — dateFrom/dateTo가 API에 전달되지 않음
4. 카드별 금액 불일치 — Transfer 처리와 Visibility 필터 적용이 API마다 다름

### 이슈 3: 필터/조회 dateFrom/dateTo 미전달 (Transaction)
- `transaction_bloc.dart:74-85` — Repository 호출에 dateFrom/dateTo 미포함 (이벤트에는 있음)
- `transaction_repository_impl.dart:16-42` — 메서드 시그니처에 dateFrom/dateTo 없음
- `transaction_remote_datasource.dart` — API 쿼리에 dateFrom/dateTo 미포함
- **BE는 준비됨**: TransactionService.listTransactions가 dateFrom/dateTo 지원
- 현재 FE가 클라이언트 사이드 필터링으로 대체 → 페이징과 조합 시 데이터 손실

### 이슈 4: 카드 금액 불일치 (Transfer/Visibility)
- `TransferRepository.kt` — visibility 필터 파라미터 없음 (모든 Transfer 포함)
- `StatisticsService.getMonthlySummary` — Transfer 포함 O
- `StatisticsService.getPeriodSummary` — Transfer totalIncome/Expense 포함, 예산 집계는 미포함
- `PaymentMethodStatisticsService` — Transfer 포함하지만 visFilter 미적용
- **결과**: 같은 기간이라도 API마다 다른 금액 반환

### 기술적 제약사항
- FE Clean Architecture: Event → BLoC → Repository → DataSource → API 전체 체인 수정 필요
- BE JPQL 쿼리 수정 시 기존 테스트 영향 확인
- Transfer visibility 필터 추가 시 TransferRepository JPQL 변경 + 호출처 전체 수정

## 성능 설계

### 데이터 접근 패턴
- **이슈 2-3 (필터 전달)**: 기존 쿼리에 WHERE 조건 추가뿐 — 추가 쿼리 없음
- **이슈 4 (Transfer visibility)**: 기존 Transfer 쿼리에 JOIN/WHERE 추가 — 추가 쿼리 없음
- **인덱스**: Transfer 테이블에 visibility 관련 조건 추가 시 `(couple_id, transfer_date, owner_id)` 인덱스 확인 필요

### 예상 규모
- 현재 데이터 규모에서 성능 영향 미미 (필터 조건 추가뿐)
- Transfer 쿼리에 JOIN 추가 시 기존 대비 10% 이내 영향

### 리소스 제약
- NAS 512MB 메모리 환경에서 쿼리 복잡도 증가 제한적
- 기존 Redis 캐시(SmartAnalysis 1일 TTL) 영향 없음

### 설계 결정
- 서버 사이드 필터링 전환 (클라이언트 사이드 필터링 제거) — 페이징 정합성 확보
- Transfer visibility는 owner 기반으로 Transaction과 동일한 패턴 적용
- 예산 집계에서 Transfer는 **제외** (예산은 카테고리 기반 → Transfer는 카테고리 없음)

## 기획 검증 결과

### 기능적 타당성
- Sprint A: Transaction/PeriodSummary 체인에 파라미터 추가 — BE가 이미 지원하므로 FE 수정이 주요 작업
- Sprint B: 인사이트 data 필드 활용 — 기존 DTO 구조에 data: Map이 이미 있어 BE 변경 최소
- Sprint C: Transfer visibility — TransferRepository JPQL 변경 필요, owner 정보 확인 필요

### Transfer Entity 구조 확인 필요
- Transfer에 `owner` 또는 `visibility` 필드가 있는지 확인 필요
- 없다면: Transfer는 커플 단위 공유 데이터로 간주하고, visibility 필터 대상에서 제외하는 것이 적합
- 이 경우 C1-C4 작업이 "Transfer는 항상 포함, 별도 visibility 없음"으로 통일되며 금액 차이의 원인이 다른 곳에 있을 수 있음

### Root Cause Prevention 체크
- **P1 (클라이언트≠서버)**: Sprint A에서 클라이언트 사이드 필터링 제거 → 서버 진실 기준 전환
- **P2 (설정 상충)**: 필터 파라미터 추가 시 기존 year/month와 dateFrom/dateTo 우선순위 명확화 (BE에서 dateFrom/dateTo 우선)
- **P3 (CI≠프로덕션)**: 신규 쿼리 변경 시 통합 테스트 추가
- **P4 (발견성)**: 인사이트 카드 네비게이션 개선으로 사용자가 관련 데이터에 접근 가능
