## 3. 계측 계획 (이 문서 §4 를 채우는 절차)

**대조군 실측 필수**(calynda 2026-08-21 교훈: 새 계측기는 변경 전에 1회 돌려 수치를 남긴다).

계측기: `frontend/test/measure_card_gap_test.dart`(일회성) —
실제 위젯을 pump 하고 `RenderBox.localToGlobal` 로 잰다. 축 3개를 **동시에** 보고한다.

1. **텍스트↔텍스트**(사용자 지표) = 카드 i 안 텍스트 최하단 → 카드 i+1 안 텍스트 최상단
2. **테두리↔테두리**(부수 지표) = `Card` rect 간 간격
3. 카드 높이(밀도 영향 확인용)

대상 (390 / 960 두 폭):
- 통계 > 카테고리별(그룹별 뷰) · 결제수단별 · 전년 비교 · 추이
- 예산 탭: `ListTile` 항목(회귀 확인, 20.0/25.0 이어야 한다) + `BudgetSummaryCard` 주변
- 주간 모드 `WeekSummaryCard` 목록

⚠ 계측 함정(기존 가드가 기록): **한 테스트에서 폭을 바꾸지 않는다**(`AnimatedTheme` 가
옛 값을 읽는다). 폭마다 테스트를 분리한다.

## 5. 구조적 수정 계획 (하네스 STRUCTURAL_FIX_REQUIRED 응답)

패치(한 파일 padding 조정)는 **불허** 판정이다. 아래 3겹으로 간다.

### 5-1. 단일 소유자 도입 — `BbCardTile` (ui_pattern)

카드형 **목록 항목**의 세로 리듬을 호출부에서 뺀다. 3차에서 `EntityTileRow` 가 우리 타일의
리듬을 소유하게 만든 것과 같은 구조다.

- 신규 `lib/core/widgets/bb_card_tile.dart` — `Card` + `InkWell` + 내부 `Padding` 을 봉인.
  호출부는 `child`(와 `onTap`)만 준다. **`margin`·`padding` 인자를 노출하지 않는다**
  (리터럴이 새려면 이 API 를 우회해야 하고 그건 `check_ui_scaling.py` 가 잡는다 — 기존
  `BbSpace` 와 같은 봉인 방식)
- 승인값은 **테스트가 소유**한다(`vertical_rhythm_guard_test` 의 `approvedTextGap`).
  위젯이 토큰에서 읽어 오면 순환 검증이 된다 — 3차 교훈
- 이관 대상(살아있는 화면의 **목록** 카드만): 통계 4탭 + `period_*` 4탭 + 예산/주간 카드
  목록. **단일 카드(요약·히어로)는 목록 항목이 아니므로 이번 축 대상이 아니다** —
  요청이 한 축이면 한 축만(3차 교훈)

### 5-2. 되돌림·누락 방지 가드 (수용 기준 ↔ 가드 매핑)

- A. 사용자 지표: 카드형 항목 사이 = 승인값 → `vertical_rhythm_guard_test` **V3 신규**
  (우리 타일 V1 · `ListTile` V1-b 와 **같은 상수**를 지나가게 묶는다 = 3계열 1승인값)
- B. 전수 적용: `Card(` 를 목록에서 직접 쓰는 곳이 0건 → **소스 스캔 가드**
  (`bb_card_tile_adoption_test`): 등재된 호스트 파일 목록에 `Card(` 생성자 부재
- C. 리터럴 회귀: `margin:`/`padding:` 에 `EdgeInsets` 리터럴을 쓴 `Card` 0건 →
  `check_ui_scaling.py` ratchet baseline 하향 + `audit_ui_consistency.py` 재확인
- D. 가로 불변: 카드 좌우 여백은 이번에 바꾸지 않는다 → V3 에 가로 단정 포함(3차와 동일)
- E. 도달성(navigation_state): 이관 대상 파일 목록을 **코드가 열거**하고, 그 목록이
  라우팅에서 도달 가능한 화면인지 가드가 확인한다(주석이 목록을 들면 어긋난다 — calynda 교훈).
  `dashboard_page` 는 목록에서 제외됨을 명시적으로 단정
- F. `[무가드]` 명시: "카드가 답답해 보이는가"(내부 여백 축소의 미감)는 기계로 못 잰다 →
  라이브 확인에 맡긴다. 테스트는 **되돌림만** 막는다

### 5-3. 예산 탭 오진 방지

사용자가 "예산에도 적용 안 됐다"고 했으나 예산 **항목**은 `ListTile`(이미 적용)이다.
→ 실측 후, 예산 탭에서 실제로 넓은 것이 무엇인지(요약 카드 주변 / 그룹 헤더 /
주간 카드 목록) **수치로 특정해 사용자에게 보고**하고, 그 대상을 이번 범위에 넣을지
사용자가 고르게 한다. 추측으로 범위를 넓히지 않는다.

## 6. 후보 사다리 (실측 후 확정 — 사용자가 값을 고른다)

3차 교훈: 체감 %를 사다리로 제시하고 승인값을 받는다. **−7% 짜리 변경을 "적용했다"고
보고하면 실패 보고가 예정된 것이다.**

실측(§4) 기준으로 후보를 다시 계산했다. 카드 계열의 사이 =
`2 × (margin 세로 + 카드 내부 padding 세로)` + 콘텐츠 자체의 꼬리 여백.

토큰 실측값 `[측정]`: `xs` 4.0/4.0 · `sm` 5.10/8.0 · `md` 6.37/10.0 · `lg` 8.0/12.0 ·
`xl` 10.2/16.0 (390/960).

- ⓐ **`margin: xs`(4) + 신규 박스역할 `cardRowPadV`(min 6, max 8.5)** →
  사이 **20.0 / 25.0** = 승인값 **정확히 일치**. 보이는 테두리 사이 8.0dp 유지
  (카드가 서로 붙지 않는다). 카테고리별 **−41.5%** · 결제수단별 −37.5% ·
  전년비교 −68% · 주간카드 −73%
- ⓑ `margin: xs` + `padding: lg`(8/12) → 24.0 / 32.0 (−29.8% / −33.3%) — 승인값 초과
- ⓒ `margin: 0` + `padding: xl`(10.2/16) → 20.4 / 32.0 — @390 만 맞고 @960 이 어긋난다.
  게다가 카드가 서로 붙는다
- ⓓ 현행 유지 + 카드형만 예외로 문서화

**선택: ⓐ**. 이유는 취향이 아니라 **이미 승인·라이브 검증된 값(20.0/25.0)에 정확히
올려놓는 유일한 후보**이기 때문이다 — 사용자 요청("모두 적용")이 요구하는 것이 그것이다.
`ListTile` 이 `listRowPadV`(10, 12.5) 라는 **전용 박스 spec** 으로 같은 값을 지나가게 만든
것과 **같은 관용구**를 쓴다(일반 여백 토큰으로는 390/960 비율 1.25 를 지나갈 수 없다 —
토큰 곡선은 1.5~1.57배다).

⚠ 귀결(사용자에게 보고): 카드 **내부** 세로 여백이 @390 에서 8.0 → 6.0 으로 25% 줄어든다
(@960 은 8.0 → 8.5 로 오히려 늘어난다). "카드가 답답하다" 판정이 나오면 레버는
`cardRowPadV.min` 하나이고, 그때는 margin 을 0 으로 옮겨 상쇄한다.

⚠ 복합 카드 2종(전년비교 62.7 · 주간카드 75.2)은 **콘텐츠 자체가 꼬리 여백을 갖는다**
(전년비교는 padding 합 32 를 빼도 8.5dp 남는다) → 래퍼 교체만으로는 승인값에 닿지 않는다.
내부 꼬리/머리 여백 제거를 함께 하고 **계측기 재실행으로 확인**한다(추정으로 종결 금지).

**사전 판정 기준**(사후 합리화 방지): 실측 텍스트 사이가 승인값(20.0)의 **1.3배 이상**이면
"미적용"으로 판정하고 이관한다. 1.1배 미만이면 이미 적용된 것으로 보고 대상에서 뺀다.
1.1~1.3배면 사용자에게 스크린샷 기준으로 되묻는다.

  1차 실패(PR #303)가 정확히 이것 — 요청하지 않은 테두리·좌우 여백을 같은 회차에 넣어
  "이전이 나았다" 판정을 받고 전량 되돌렸다. 다음 회차(비목록 카드)로 넘긴다.
