## 2. 실측 — 무엇이 행 높이를 지배하나 `[측정 2026-08-21, 위젯 렌더 기하]`

`EntityTileRow` 2개를 나란히 렌더해 실제 픽셀을 읽었다(320/390/960).

- **행 높이 = 48.0dp @390**, **인접 제목 간 거리도 48.0dp** → 행 사이 gap 은 **0**이다.
  즉 "항목 간 여백"의 정체는 **행 높이 그 자체**다.
- 구성: **아바타 32.0dp = 67%** + `padV`(lg 8.0)×2 = 16.0dp = **33%**
- @960: 행 64.0 = 아바타 40 + padV(lg 12)×2
- 칩 있는 카드 타일: **71.2dp @390** / 94.0 @960
- 제목 폰트(section) 14.0 @390 — 텍스트 줄은 ~16.4dp 로 **아바타보다 훨씬 작다**

**따라서 1차 변경(`padV` 8 → 6.37)은 행을 48.0 → 44.7dp, 즉 −6.8% 만 줄였다.**
사용자가 "동일하거나 넓다"고 느낀 것은 정확한 관찰이다 — 지배 변수를 안 건드렸다.

### 선택지와 수치 (기준 48.0dp @390)

- (a) `padV` md → **44.7** (−6.8%) ← **1차에서 실패한 값**
- (b) `padV` sm → **42.2** (−12.1%)
- (c) **`padV` xs, 아바타 유지 → 38.0 (−20.8%)** ← 권장. @960 48.0 (−25.0%)
- (d) 아바타 28 + `padV` sm → 38.2 (−20.4%)
- (e) 아바타 24 + `padV` md → 36.7 (−23.5%)

**권장 (c)** 이유: ① 토큰 **한 곳**(`entity_tile_row.dart` 의 `vertical:`)만 바뀐다
② 아바타·폰트 등 **사용자 승인값을 건드리지 않는다**(1차 실패의 교훈) ③ 되돌리기 한 줄
④ (d)와 체감 수치가 같은데 변경 표면이 절반이다.

**트레이드오프(명시)**: 행 높이 38dp 는 **44dp 터치 하한 미달**이다 `[1차: L4-2]`.
행은 화면 폭 전체를 쓰므로(390×38) 세로만 줄어드는 형태이지만, 규격 위반은 위반이다.
**사전 판정 기준** — 누르기 불편하다는 보고가 오면 (b) 42.2dp 로 한 단계 되돌린다.

  → **왼쪽에 죽은 여백 + 오른쪽 21dp 잘림**. 360px 51dp, 320px 91dp 잘림.
- **처방**: `tabAlignment: TabAlignment.center`
  실측 @390 → 첫 라벨 39.6 / 마지막 끝 370.5 / 오른쪽 여유 19.5 = **전부 들어가고 좌우 균형**
  (콘텐츠 359 < 390). 320/360 은 여전히 스크롤이지만 52dp 죽은 여백은 사라진다.
- **공통 적용 범위 전수** `[측정]`: 스크롤 TabBar 는 앱에 **3곳** —
  `statistics_page`(아이콘+라벨 4개) · `period_summary_page`(텍스트 4개, 첫 라벨 x=60) ·
  `feedback_hub_page`(텍스트 3개, 첫 라벨 x=60). **셋 다 같은 결함**이므로 함께 고친다
  (`feedback_common_scope_audit` — 한 곳만 고치는 것 금지).
  나머지 6곳은 비스크롤(폭 채움)이라 해당 없음.
