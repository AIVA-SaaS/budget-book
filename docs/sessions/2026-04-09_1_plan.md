## Part 1: 통합 가계부 전환 (Self-Couple 방식)

### 아키텍처 결정: 방안 A — Self-Couple

**선택 이유**: 14개 테이블, 18+ 서비스, 50+ 쿼리를 건드리지 않고 최소 변경으로 구현 가능.

**핵심 개념**: 개인 사용자 가입 시 `couples` 테이블에 `(user1_id=self, user2_id=NULL, status=ACTIVE)` 레코드 자동 생성. 기존 `couple_id` 기반 전체 아키텍처 유지.

### 영향 범위 분석

| 영역 | 변경 | 비변경 |
|------|------|--------|
| DB | V48: 기존 사용자 self-couple 백필 | 14개 테이블 구조 유지 |
| BE 가입 | OAuth2UserService: self-couple 자동 생성 | CoupleResolver, 18+ 서비스 전체 유지 |
| BE 커플 | CoupleService: 커플 합류(2인화) 로직 추가 | 기존 초대/수락/해산 유지 |
| FE 온보딩 | 커플 등록을 선택사항으로 변경 | 전체 기능 페이지 변경 없음 |
| FE 라우터 | coupleId null 강제 리다이렉트 제거 | 나머지 라우팅 유지 |
| FE 설정 | "파트너 초대" 기능으로 이동 | 기존 설정 항목 유지 |
| FE UI | 서비스명 "Budget Book" 변경, 커플 전용 UI 분기 | 핵심 기능 UI 동일 |

### 작업 상세

#### 1-1. DB 마이그레이션 (V48)
```sql
-- 기존 커플 없는 사용자에게 self-couple 생성
INSERT INTO couples (id, user1_id, user2_id, status, created_at, updated_at)
SELECT gen_random_uuid(), u.id, NULL, 'ACTIVE', NOW(), NOW()
FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM couples c 
    WHERE c.user1_id = u.id OR c.user2_id = u.id
);
```
- CHECK 제약 `ck_couples_different_users` (`user1_id <> user2_id`) → user2_id=NULL이면 UNKNOWN → PostgreSQL CHECK 통과 ✓
- 난이도: S

#### 1-2. BE: 가입 시 self-couple 자동 생성
- **파일**: `CustomOAuth2UserService.kt`, `CustomOidcUserService.kt`
- 신규 사용자 생성 직후 self-couple 자동 생성
- `CoupleService.createSelfCouple(userId)` 메서드 추가
- 난이도: S

#### 1-3. BE: 커플 합류(2인화) 로직
- **파일**: `CoupleService.kt`
- 기존 초대코드 수락 시: 수락자의 self-couple 데이터를 초대자의 couple로 마이그레이션
  - 방식: 수락자의 모든 테이블에서 `couple_id = self_couple_id` → `couple_id = target_couple_id` UPDATE
  - 수락자의 self-couple을 DISSOLVED로 변경
  - 초대자의 couple에 user2_id = 수락자 설정
- 커플 해제 시: 양쪽 사용자에게 각각 self-couple 재생성
- 난이도: M

#### 1-4. FE: 온보딩 플로우 변경
- **파일**: `app_router.dart`, `couple_page.dart`
- 가입 후 coupleId null 체크 리다이렉트 제거 (self-couple이므로 항상 coupleId 존재)
- 최초 로그인 시 "개인 가계부로 시작" / "파트너와 함께 시작" 선택 화면
- "파트너와 함께 시작" 선택 시 기존 초대코드 플로우
- "개인으로 시작" 선택 시 바로 홈으로 이동
- 난이도: M

#### 1-5. FE: 설정에서 파트너 관리
- **파일**: `settings_page.dart`, 신규 `partner_management_page.dart`
- 설정 > "파트너 관리" 메뉴 추가
- 커플 미등록(self-couple) 시: "파트너 초대하기" 버튼
- 커플 등록 시: 파트너 정보 표시 + "커플 해제" 버튼
- 난이도: M

#### 1-6. FE: 커플 전용 기능 분기
- 커플 미등록(user2_id=null) 시 숨기거나 비활성화할 기능:
  - 공유 알림 / WebSocket 파트너 동기화 표시
  - "나만 보기" 토글 (의미 없으므로 숨김)
  - 파트너 프로필 영역
- `CouplePrefs`에 `isCouple` getter 추가하여 분기
- 난이도: S

#### 1-7. 서비스명 변경
- FE: `AppBar` 타이틀, 로그인 페이지, 소개 텍스트 등에서 "Budget Book" → "통합 가계부" 또는 적절한 이름
- BE: `application.yml` app name (영향 없음)
- 난이도: S

### 커플 합류 시 데이터 병합 전략

```
A(개인, self-couple-A) + B(개인, self-couple-B)
  ↓ B가 A의 초대코드 수락
A의 couple에 B 합류:
  1. B의 모든 데이터 (transactions, budgets, categories...) → couple_id를 A의 couple_id로 UPDATE
  2. B의 데이터는 visibility=PRIVATE, owner_id=B.id 유지 (B만 보이게)
  3. B의 self-couple → DISSOLVED
  4. A의 couple → user2_id = B.id
```

## Part 2: 날짜별 사용 기록 모아보기

### 개요
기간별(특정 주, 월, 날짜 범위) 카테고리별/예산별/결제수단별 사용 금액을 종합 표시하는 새 페이지.

### 작업 상세

- 난이도: M

#### 2-2. FE: 기간별 기록 페이지 (신규)
- **경로**: `/period-summary`
- **진입점**: 홈 또는 통계 탭에서 접근
- **구성**:
  1. 상단: 기간 선택기 (공통 필터 모듈 사용 — Part 3)
  2. 요약 카드: 총 수입/지출/잔액
  3. 탭 뷰:
     - **카테고리별**: 그룹 > 카테고리 트리 + 금액 + 비율 바
     - **예산별**: 예산명 + 사용/남은 금액 + 진행 바
     - **결제수단별**: 결제수단별 금액 + 건수
     - **일별**: 날짜별 수입/지출 미니 차트
  4. 하단: 필터 영역 (카테고리, 결제수단, 포켓 선택/해제)
- 난이도: L

#### 2-3. FE: 필터 연동
- 공통 필터 모듈(Part 3)과 연동
- 카테고리 선택/해제 시 실시간 재계산 (클라이언트 또는 서버)
- 결제수단, 포켓도 동일 필터 적용
- 난이도: M (Part 3에 의존)

#### 3-1. 공통 필터 모델 (FE)

```dart
class UnifiedFilterState {

  bool get hasActiveFilters => ...;
  UnifiedFilterState copyWith(...);

```

#### 3-2. 공통 필터 위젯 (FE)
```
core/widgets/filters/
├── unified_filter_bar.dart      — 필터 칩/버튼 바 (활성 필터 표시)
├── date_range_filter.dart       — 기간 선택 (프리셋 + 직접 설정)
├── category_filter.dart         — 카테고리 다중 선택 (그룹별)
├── payment_method_filter.dart   — 결제수단 다중 선택
├── amount_range_filter.dart     — 금액 범위 입력
├── filter_bottom_sheet.dart     — 통합 필터 바텀시트 컨테이너
└── filter_chip_group.dart       — 상태/타입 필터 칩 그룹
```

#### 3-3. 사용 패턴
```dart
// 각 페이지에서 사용
UnifiedFilterBar(
  state: filterState,
  enabledFilters: {FilterType.dateRange, FilterType.category, FilterType.paymentMethod},
  onFilterChanged: (newState) => bloc.add(ApplyFilter(newState)),
)
```
- `enabledFilters`로 페이지별 필요한 필터만 표시
- 동일한 위젯이 거래 목록, 통계, 기간별 기록, 리포트에서 사용

#### 3-4. 기존 페이지 리팩토링

## 성능 설계

### 데이터 접근
- **self-couple 조회**: 기존 `CoupleResolver` 그대로 → 추가 쿼리 0
- **커플 합류 데이터 병합**: 14개 테이블 UPDATE (1회성) → 트랜잭션으로 원자성 보장
- **기간별 통계**: 기존 인덱스 `idx_transaction_couple_date` 활용, GROUP BY 집계 쿼리
- **필터 위젯**: 클라이언트 사이드 필터 상태 → API 호출은 debounce 300ms

### 예상 규모
- self-couple 백필: 기존 사용자 수 (수십 명 이내)
- 기간별 통계: 월 100~500건 거래 기준 GROUP BY → 수 ms

### 리소스 제약
- NAS 512MB: 집계는 DB에서 처리, 앱 메모리 영향 없음
- 커플 합류 14개 테이블 UPDATE: 배치 처리, 커넥션 1개 사용
