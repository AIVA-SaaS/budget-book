## Phase 1: 보안 + 데이터 정합성 (즉시 수정 필수)

### P1-1. [SEC-Critical] WebSocket 구독 인가 없음
- **문제**: 인증된 사용자가 `/topic/couple/{아무ID}`를 구독하여 다른 커플의 실시간 이벤트 수신 가능
- **추가**: WebSocket CORS가 `*`로 열려있어 외부 사이트에서도 연결 가능
- **수정**: `WebSocketAuthInterceptor`에 SUBSCRIBE 시 coupleId 소속 검증 + CORS를 프론트엔드 도메인으로 제한
- **담당**: BE

### P1-2. [SEC-High] 3개 쿼리에서 visibility 필터 누락
- **문제**: `sumByPaymentMethodAndSettlementDateRange`, `sumBySettlementDateGroupedByPaymentMethod`, `sumExpenseByPocketId` — PRIVATE 거래가 상대방에게 노출
- **수정**: 3개 쿼리에 `(visibility = SHARED OR owner_id = :userId)` 조건 추가
- **담당**: BE

### P1-3. [SEC-High] OAuth2 콜백에서 토큰이 URL 쿼리 파라미터로 노출
- **문제**: `?accessToken=...&refreshToken=...`이 브라우저 히스토리, 서버 로그, Referer 헤더에 기록
- **수정**: 일회용 authorization code 패턴으로 변경 또는 HttpOnly 쿠키 사용
- **담당**: BE

### P1-4. [BE-Critical] ReportService 쿼리가 visibility 필터 우회
- **문제**: 리포트에서 PRIVATE 예산/그룹이 상대방에게 노출
- **수정**: `findByCoupleIdAndYearMonthAndUserId`, `findByCoupleIdAndUserIdOrderByDisplayOrder` 사용
- **담당**: BE

### P1-5. [BE-Critical] 반복거래 실행 시 visibility 미전파
- **문제**: `executeRecurringTransactions()`에서 생성되는 거래가 항상 SHARED (카테고리가 PRIVATE이어도)
- **수정**: `category?.visibility ?: Visibility.SHARED`로 파생 + owner 설정
- **담당**: BE

### P1-6. [BE-Critical] 그룹 visibility 변경 시 하위 카테고리 cascade 없음
- **문제**: PRIVATE 그룹에 SHARED 카테고리가 존재 가능 → 상대방에게 노출
- **수정**: 그룹 visibility 변경 시 하위 카테고리 + 관련 거래 chain cascade
- **담당**: BE

### P1-7. [DB-Critical] ON DELETE SET NULL + visibility CHECK 충돌
- **문제**: User 삭제 시 5개 테이블에서 owner_id=NULL이 되지만 visibility=PRIVATE이 유지되어 CHECK 위반 → DB 에러
- **수정**: BEFORE DELETE 트리거로 PRIVATE→SHARED 변환, 또는 ON DELETE RESTRICT
- **담당**: DB

### P1-8. [DB-Critical] money_pockets, pocket_transfers FK ON DELETE 미지정
- **문제**: couple 삭제 시 FK 위반 에러
- **수정**: ON DELETE CASCADE 추가
- **담당**: DB

### P1-9. [DB-Critical] BANK CHECK constraint 누락 (V30 미배포)
- **문제**: BANK 결제수단 등록 불가
- **수정**: V30 마이그레이션 (이미 작성됨, 배포 필요)
- **담당**: DB

## Phase 2: 데이터 모델 + API 일관성

### P2-1. [BE-Critical] DTO 응답 형식 불일치 (3가지 카테고리 표현 혼재)
- **문제**: TransactionResponse=CategorySummary 중첩, WeeklyBudgetItem=flat ID/Name, BudgetAlert=String categoryId
- **수정**: 모든 엔드포인트에서 `CategorySummary?` 중첩 객체 통일
- **담당**: BE + FE

### P2-2. [FE-Critical] recurring 모델이 category 중첩 객체를 flat 파싱
- **문제**: `json['categoryId']`/`json['categoryName']`으로 파싱하지만 BE는 `category: {}` 중첩 반환
- **수정**: 중첩 파싱으로 변경 + displayName 포함
- **담당**: FE

### P2-3. [FE-Major] BudgetSummaryItem에 groupId 없음
- **문제**: 그룹별 예산 사용금액이 모두 동일하게 표시
- **수정**: groupId/groupName 파싱 + _findSummaryItem에서 groupId 매칭
- **담당**: FE

### P2-4. [BE] 예산 visibility가 카테고리/그룹에서 파생되지 않음
- **문제**: SHARED 예산이 PRIVATE 카테고리를 참조 가능 → 개인 카테고리 존재 노출
- **수정**: 거래와 동일하게 카테고리/그룹 visibility에서 파생
- **담당**: BE

### P2-5. [DB-High] budget_period 컬럼 미제거 (period_type과 중복)
- **문제**: 두 컬럼이 동시 존재하여 값 모순 가능
- **수정**: budget_period DROP + JPA 엔티티 정리
- **담당**: DB + BE

### P2-6. [BE] ReportService 주간 계산이 WeeklyBudgetService와 다름
- **문제**: 리포트는 고정 7일, 주간예산은 월~일 경계 → 같은 "2주차"가 다른 날짜
- **수정**: WeeklyBudgetService.calculateWeekRanges 공통 사용
- **담당**: BE

### P2-7. [BE] CreateTransactionRequest의 dead visibility 필드
- **문제**: request에 visibility 필드 있지만 서비스에서 무시 → API 소비자 혼란
- **수정**: DTO에서 제거
- **담당**: BE

## 구조적 재발 방지 방안

### 1. API 응답 계약 표준화
모든 엔티티 참조는 중첩 Summary 객체로 통일:
```
CategorySummary { id, name, type, icon, color, groupId, groupName }
PaymentMethodSummary { id, name, type }
GroupSummary { id, name, icon, color, budgetType }
```
→ FE에서 flat 파싱 / 중첩 파싱 혼재 문제 원천 차단

### 2. Visibility 규칙 중앙화
```
VisibilityResolver.deriveForTransaction(category) → Visibility
VisibilityResolver.deriveForBudget(category, group) → Visibility
VisibilityResolver.cascadeGroupChange(group, newVisibility) → void
```
→ 서비스마다 다른 visibility 처리 로직 통일

### 3. FE 공통 유틸 레이어
```
core/utils/
├── currency_formatter.dart   (기존 확장)
├── date_helpers.dart         (신규)
├── payment_method_helpers.dart (신규)
├── snackbar_helpers.dart      (신규)
├── dialog_helpers.dart        (신규)
└── ui_helpers.dart            (기존 - parseColor/resolveIcon 통합)
```
→ 중복 코드 원천 차단

### 4. SharedPreferences 네임스페이싱
```dart
class CouplePrefs {
  static String _key(String coupleId, String name) => '${coupleId}_$name';
  static Future<void> clearAll(String coupleId) async { ... }
}
```
→ 커플 변경 시 stale 데이터 문제 원천 차단

### 5. CI 검증 강화
- `flutter analyze` 에러 0건 필수 (이미 적용)
- BE: `DataIntegrityViolationException` 테스트 추가
- DB: 마이그레이션 후 JPA validate 검증
