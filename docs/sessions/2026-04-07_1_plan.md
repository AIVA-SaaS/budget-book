## Part A: 버그 수정 (Critical — 우선 처리)

### BUG-1: 거래 삭제 후 네비게이션 오류
- **현상**: 거래 삭제 시 이전 화면으로 이동 안됨. 거래 수정 화면에 머물러 있다가, 뒤로 가면 "Transaction does not exist" 표시
- **코드 확인 결과**: `transaction_form_page.dart:396-420`에 BlocListener가 있고, 삭제 성공 시 `context.go('/transactions')` (line 407) 호출하는 로직이 존재함. 그러나 조건 분기에서 삭제 후 `operationSuccess` 메시지가 정상 emit되지 않거나, BlocListener가 해당 상태를 감지하지 못하는 경우가 있을 수 있음
- **수정 방향**:
  - FE: BlocListener의 삭제 성공 분기 조건 디버깅 — `operationSuccess`가 '거래가 삭제되었습니다'일 때 `context.go('/transactions')` 경로가 실제 동작하는지 확인
  - 상태 emit 시 `operationSuccess` 필드가 누락되는 케이스 점검 (예: catch 블록에서 빠지는 경우)
  - transaction_detail_page에서의 삭제 플로우도 동일하게 점검
- **영향 파일**: `transaction_detail_page.dart`, `transaction_form_page.dart`, `transaction_bloc.dart`
- **난이도**: S

### BUG-2: 카테고리 하위 추가 불가 (미분류 > 전체 불가)
- **현상**: 카테고리에 하위 카테고리 추가가 불가능
- **원인 분석**: `CategoryPage`에서 카테고리 추가 시 `groupId` 파라미터를 전달하는 UI가 없거나, 특정 그룹("미분류")에 대한 제약이 있을 수 있음
- **수정 방향**:
  - FE: 카테고리 관리 → 그룹 선택 → 하위 카테고리 추가 플로우 확인 및 수정
  - BE: `CategoryController.createCategory` API에 `groupId` 파라미터 전달 확인
- **영향 파일**: `category_page.dart`, `category_form_sheet.dart`, `CategoryController.kt`
- **난이도**: S

### BUG-3: 카테고리/결제수단 수정 기능 없음
- **현상**: 추가/삭제는 가능하나 기존 항목 수정(이름, 아이콘, 색상 등) 불가
- **원인 분석**: BE에는 PUT API가 존재할 가능성 높으나, FE UI에 수정 진입점(편집 버튼/스와이프)이 없음
- **수정 방향**:
  - FE: 카테고리 항목 탭 → 수정 바텀시트 표시 (기존 `category_form_sheet.dart` 재활용)
  - FE: 결제수단 항목 탭 → 수정 바텀시트 (기존 `payment_method_form_sheet.dart` 재활용)
  - BE: PUT API 존재 여부 확인, 없으면 추가
- **영향 파일**: `category_page.dart`, `category_form_sheet.dart`, `payment_method_page.dart`, `payment_method_form_sheet.dart`
- **난이도**: M

### BUG-4: 4월 카드 미결제액과 이전달 사용 총액 불일치
- **현상**: 카드 기준 미결제액이 이전달 실제 사용 총액과 다름
- **원인 분석**: `CardAutoSettlementScheduler`와 미결제 금액 계산 로직의 정산일 기준 차이, 또는 이체 금액 미포함 가능
- **수정 방향**:
  - BE: `PaymentMethodService`의 미결제 금액 산출 쿼리 검증 (정산일 범위, 이체 포함 여부)
  - FE: `card_pending_summary.dart`의 표시 로직 대조
- **영향 파일**: `PaymentMethodService.kt`, `PaymentMethodRepository.kt`, `card_pending_summary.dart`
- **난이도**: M

## Part B: 예산 시스템 수정 (High Priority)

### B-1: 예산 금액 불일치 수정
- **현상**: "생활비"와 "장" 다른 항목인데 같은 금액으로 표시 + 상위 총 예산 금액과 각 예산 사용 금액 불일치
- **원인 분석**: BudgetSummary에서 그룹 예산과 하위 카테고리 예산이 이중 집계되거나, spent 금액이 카테고리 필터링 없이 집계될 가능성
- **수정 방향**:
  - BE: `BudgetService.getBudgetSummary()` — 그룹 예산 vs 카테고리 예산의 spent 계산 검증
  - FE: budget list에서 각 항목의 `spent` 값이 올바른 카테고리 필터로 조회되는지 확인
- **영향 파일**: `BudgetService.kt`, `WeeklyBudgetService.kt`, budget BLoC/페이지
- **난이도**: M

### B-2: 예산 수정 시 카테고리 "그룹 > 하위" 형태 미표시
- **현상**: 예산 수정 폼의 카테고리 선택기에서 상위 그룹 > 하위 카테고리 계층 표시 안됨
- **수정 방향**:
  - FE: 예산 폼의 카테고리 선택기에 `CategoryGroupSelectorSheet` 적용 확인
  - 선택된 카테고리 표시 시 `그룹명 > 카테고리명` 형식으로 표시
- **영향 파일**: budget form page, `CategoryGroupSelectorSheet`
- **난이도**: S

### B-3: 구매 목록 예산 연결 — 주간 예산 표시 오류
- **현상**: 예산 연결에서 주간 예산이 단순 `*4주`로 표시됨
- **기대 동작**: 
  1. 주간 예산은 일할 계산으로 월 환산 금액 표시
  2. 예산 선택 시 "4월 (첫째주)", "4월 (둘째주)" 등 주차별로 각각 표시
  3. 날짜 선택 기준에 맞는 해당 주 예산만 표시
- **수정 방향**:
  - FE: 구매 목록의 예산 선택 위젯에서 주간 예산 표시 로직 수정
  - 선택된 날짜 기준으로 해당 주의 주간 예산만 필터링하여 표시
  - 금액은 주간 원래 금액 표시 (×4가 아닌 실제 주간 할당 금액)
- **영향 파일**: wishlist budget selector widget, budget BLoC
- **난이도**: M

### B-4: 주간 예산 일할 계산 1원 오차 수정
- **현상**: 이전달/다음달 걸치는 경우 round 처리로 1원이 부족한 케이스 발생
- **수정 방향**:
  - BE: 일할 계산 시 마지막 주에서 `주 예산 - 이전 주들 합계`로 잔여 배정 (단순 round가 아닌 차감 방식)
  - 예: 월 예산 100,000원, 4.3주 → 1~3주: round(100000/4.3)=23,256원씩 → 4주: 100,000 - 23,256×3 = 30,232원
- **영향 파일**: `WeeklyBudgetService.kt`, 관련 일할 계산 유틸
- **난이도**: S

## 성능 설계

### 데이터 접근 패턴
- **B-1 예산 집계**: 기존 GROUP BY 쿼리에 카테고리/그룹 필터 정확성 보장. N+1 방지를 위해 단일 집계 쿼리 유지
- **C-3 기간 필터**: 기존 `dateFrom/dateTo` 인덱스 활용. 새 인덱스 불필요 (이미 `idx_transaction_couple_date` 존재)
- **C-7 예산-계획 연동**: 예산 조회 시 spending_plan 테이블 추가 조회 1회 (카테고리별 PENDING 합계)
- **C-9 정산**: 주간 단위 조회이므로 데이터 양 제한적 (주당 최대 수십 건)

### 예상 규모
- 카테고리: 커플당 20~50개
- 예산: 월별 10~30개
- 거래: 월별 100~500건
- 계획: 월별 10~30개

### 리소스 제약
- NAS Docker: 512MB BE 메모리 → 집계 쿼리는 DB에서 처리, 앱 메모리에 전체 로딩 방지
- PostgreSQL: 커넥션 풀 10개 → 병렬 쿼리 제한 고려

### 설계 결정
- 정산 이력은 별도 테이블 (weekly_budget_settlements) — 기존 예산 테이블 변경 최소화
- 거래 연결은 nullable FK로 구현 — 연결 해제 가능하게
- 계산기 입력은 FE only — BE에 수식 전달 불필요
