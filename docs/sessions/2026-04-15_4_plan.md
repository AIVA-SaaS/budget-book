# Phase 20-D: Phase 20-C 기존 데이터 마이그레이션 + 확인
> 날짜: 2026-04-15 | 회차: 4 | 상태: 승인

## 문제
Phase 20-C 배포 이후에도 사용자가 "이전 문제 재현"을 신고:
- 결제했는데 미결제 금액에 계속 표시
- 전월/이번달/결제 상황 금액 이상

## 원인 분석

### 코드 상태 (정상)
- `buildMonthByTransactionDate`: paid_at 필터 없음 → 전월/이번달 사용 = 모든 거래 합 (정상)
- `buildMonthBySettlementDate`: paid_at IS NULL 필터 있음 → 미결제 = 결제되지 않은 거래만 (정상)
- 통계 서비스: sumAmountBy*ExcludingSettlement 사용 (정상)

### 기존 데이터 문제 (비정상)
**Phase 20-C (V51/V52) 배포 이전에 생성된 데이터**:
- 기존 결제 이체: `is_card_settlement = false` (default) → 카드 결제로 인식 안 됨
- 기존 원본 거래: `paid_at = null` → 결제된 것으로 처리 안 됨

**결과**:
1. 기존 결제 이체가 일반 이체로 취급되어 unpaidMonth의 transferOut에 포함 → 이중 계산
2. 기존 원본 거래가 paid_at=null이므로 미결제로 계속 표시

## 구조적 수정 계획

### V53 데이터 마이그레이션
**기존 BANK→CREDIT 이체를 카드 결제로 표시**:
```sql
UPDATE transfers
SET is_card_settlement = true
WHERE is_card_settlement = false
AND source_payment_method_id IN (SELECT id FROM payment_methods WHERE type = 'BANK')
AND destination_payment_method_id IN (SELECT id FROM payment_methods WHERE type = 'CREDIT');
```
근거: BANK→CREDIT 조합 이체는 99% 카드 결제 용도. 일반 목적의 이체 가능성 매우 낮음.

**기존 결제 이체의 대응 거래에 paid_at 자동 설정**:
각 결제 이체에 대해, 해당 이체의 destination 카드에서 transferDate 월에 settlementDate가 있는 거래의 paid_at을 transferDate로 설정.

```sql
UPDATE transactions t
SET paid_at = sub.transfer_date
FROM (
    SELECT DISTINCT ON (t_inner.id)
        t_inner.id as txn_id,
        tr.transfer_date
    FROM transactions t_inner
    JOIN transfers tr ON tr.destination_payment_method_id = t_inner.payment_method_id
    WHERE t_inner.paid_at IS NULL
    AND t_inner.settlement_date IS NOT NULL
    AND tr.is_card_settlement = true
    AND EXTRACT(YEAR FROM tr.transfer_date) = EXTRACT(YEAR FROM t_inner.settlement_date)
    AND EXTRACT(MONTH FROM tr.transfer_date) = EXTRACT(MONTH FROM t_inner.settlement_date)
    ORDER BY t_inner.id, tr.transfer_date DESC
) sub
WHERE t.id = sub.txn_id;
```
근거: 결제 이체가 이루어진 월 = 그 달에 결제되어야 할 거래들(settlementDate이 그 달)을 결제한 것으로 간주. 부분 결제 사례는 거의 없음.
