## 2. 문제 발생 원인 분석

### A/B. 온보딩 이동 불가 (웹+모바일 공통)

**근본 원인**: `app_router.dart` 리다이렉트 로직에서 `_onboardingCompleted` 플래그가 `false`이면 **무조건** `/onboarding`으로 보냄. `user.coupleId`가 이미 있어도 무시.

```
// app_router.dart:118
if (!_onboardingCompleted) return '/onboarding';  // ← coupleId 체크 없이 무조건 리다이렉트
```

**문제 시나리오**:
1. 사용자가 이미 커플 연결된 상태로 새 디바이스/브라우저에서 로그인
2. SharedPreferences에 `onboardingCompleted = false` (새 디바이스이므로)
3. `coupleId`가 있음에도 온보딩 페이지로 강제 이동
4. 온보딩 Step 2 "커플 연결하기" 표시 → 이미 커플인데 혼란
5. **"시작하기" 버튼은 Step 3에서만 표시** → Step 2에서 막힘

**추가 문제**: `onboarding_page.dart`에서 "커플 연결하기" 버튼이 `context.push('/couple')` 사용 → 뒤로가기 시 다시 온보딩으로 돌아옴 (무한 루프 가능)

### C. 결제수단 등록 문제

**조사 결과**: BE/FE 모두 구현 자체는 되어 있음.
- BE: `@NotBlank` name, enum type (CASH/DEBIT/CREDIT), CREDIT은 `settlementDay`+`closingDay` 필수
- FE: `PaymentMethodFormSheet`에 name 빈값 검증 + type SegmentedButton 있음

**가능한 원인**:
1. FE form에서 CREDIT 타입 선택 시 `settlementDay`/`closingDay` UI가 제대로 노출되지 않거나, 값 전달 실패
2. BLoC → Repository → API 호출 경로에서 request body 직렬화 문제
3. API 에러 응답이 사용자에게 표시되지 않음 (에러 핸들링 누락)
→ **실제 코드를 읽어서 정확한 원인 확인 필요** (개발 단계에서 상세 디버깅)

### D. 카테고리/결제수단 삭제 기능

**조사 결과**: BE DELETE 엔드포인트 + FE 삭제 UI **모두 이미 구현되어 있음**.
- 카테고리: `CategoryPage`에 삭제 다이얼로그 + `DELETE /api/v1/categories/{id}`
- 결제수단: `PaymentMethodPage`에 스와이프 삭제 + `DELETE /api/v1/payment-methods/{id}`
- 기본(default) 항목은 삭제 불가 (정상)

**가능한 원인**:
1. 스와이프 삭제가 직관적이지 않아 사용자가 발견하지 못함
2. 삭제 UI가 실제로 동작하지 않음 (BLoC 이벤트 연결 문제)
3. 기본 카테고리/결제수단만 있어서 삭제 불가 상태
→ **삭제 UI 발견성 개선 + 동작 검증 필요**

### E. `/login?error=authorization_request_not_found`

**근본 원인**: **SessionCreationPolicy.STATELESS + 기본 OAuth2 AuthorizationRequestRepository 충돌**

```kotlin
// SecurityConfig.kt:36
.sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) }
```

**문제 흐름**:
1. 사용자가 "Google 로그인" 클릭 → BE가 Google로 리다이렉트
2. Spring Security가 OAuth2 인증 요청(state, nonce 등)을 **HTTP 세션에 저장** (기본 동작)
3. 그러나 `STATELESS` 정책으로 **세션이 생성되지 않음**
4. Google 인증 완료 → BE 콜백으로 돌아옴
5. Spring이 세션에서 인증 요청을 찾으려 하지만 → 세션 없음
6. `authorization_request_not_found` 에러 발생
7. `OAuth2AuthenticationFailureHandler`가 `{frontendUrl}/login?error=...`로 리다이렉트

**해결**: `HttpCookieOAuth2AuthorizationRequestRepository` 사용 (쿠키 기반 state 저장)

### F. CI 빌드 실패 알림 지속

**근본 원인**: **Deploy Backend workflow가 계속 실패** (최근 10회 연속 실패)

**원인 분석**:
1. CI는 `profile=local`로 테스트 → 통과
2. Render 배포는 `profile=prod`로 실행 → 실패
3. **CI에서 prod 프로필 검증을 하지 않음** → 환경 차이 감지 불가
4. Deploy workflow가 main push마다 트리거 → 매번 실패 → 매번 Issue 생성

**환경 차이**:
| 항목 | CI (local) | Prod (render) |
|------|-----------|---------------|
| DB | PostgreSQL container | Supabase (sslmode=require) |
| Session | - | STATELESS |
| 메모리 | 무제한 | 512MB |
| Connection Pool | 기본값 | hikari max=5, timeout=20s |

## 3. 작업 계획

| # | 작업 | 담당 | 파일 | 난이도 |
|---|------|------|------|--------|
| 1 | 온보딩 로직 수정: coupleId 있으면 자동 완료 | FE | `app_router.dart`, `onboarding_page.dart` | M |
| 2 | OAuth2 쿠키 기반 AuthorizationRequestRepository 구현 | BE | `SecurityConfig.kt`, 신규 Repository 클래스 | M |
| 3 | 결제수단 등록 디버깅 + 수정 | FE+BE | `payment_method_form_sheet.dart`, 관련 BLoC | M |
| 4 | 삭제 UI 발견성 개선 (명시적 삭제 버튼 추가) | FE | `payment_method_page.dart`, `category_page.dart` | S |
| 5 | CI에 prod 프로필 검증 추가 | DevOps | `ci-backend.yml` | S |
| 6 | Deploy 실패 알림 중복 방지 | DevOps | `deploy-backend.yml` | S |

### 실행 순서
```
Phase 1 (병렬):
  - BE: OAuth2 AuthorizationRequestRepository (작업 2)
  - FE: 온보딩 로직 수정 (작업 1)
  - FE: 결제수단 등록 디버깅 (작업 3)

Phase 2 (병렬, Phase 1 완료 후):
  - FE: 삭제 UI 개선 (작업 4)
  - DevOps: CI/CD 수정 (작업 5, 6)

Phase 3: 교차 검증 + 통합 테스트
```

## 성능 설계
- **데이터 접근**: 변경 없음 (기존 쿼리 패턴 유지)
- **예상 규모**: 영향 없음 (버그 수정 위주)
- **리소스 제약**: OAuth2 쿠키 저장은 클라이언트 사이드 → 서버 메모리 절약
- **설계 결정**: `HttpCookieOAuth2AuthorizationRequestRepository`는 Spring Security 공식 제공 클래스 사용 (커스텀 구현 불필요)

## 기획 검증 결과

### 기능적 타당성 ✅
1. **온보딩**: coupleId 체크를 라우터 리다이렉트에 추가하는 것은 안전. 기존 신규 유저 플로우에 영향 없음.
2. **OAuth2**: `HttpCookieOAuth2AuthorizationRequestRepository`는 Spring Security 공식 솔루션. STATELESS 세션과 호환.
3. **결제수단**: 기존 구현 디버깅이므로 신규 위험 없음.
4. **삭제 UI**: 기존 백엔드 API 활용, FE만 개선.
5. **CI/CD**: prod 프로필 검증 추가는 기존 CI 파이프라인 확장.

### 기존 코드 충돌 ✅
- SecurityConfig 변경: OAuth2 설정에 `authorizationRequestRepository` 추가만 (기존 설정 유지)
- Router 변경: 리다이렉트 조건 추가 (기존 로직 위에 early return 삽입)
- CI 변경: 기존 step 이후 추가 step (기존 workflow 영향 없음)

### 보안 ✅
- 쿠키 기반 OAuth2 state: SameSite + Secure 설정 필수
- 기존 JWT 인증 체계 변경 없음
