## 성능 설계 (원칙 1.4)
- **데이터 접근**: `LoadTransactions` 는 `/api/v1/transactions?year&month` 1회 호출 (기존 API). 신규 쿼리 0.
- **예상 규모**: 월별 거래 건수 평균 100건 내외. 페이지 크기 영향 없음.
- **연산 복잡도**: BLoC state diff 기반 rebuild. O(N) N=거래수.
- **리소스 제약**: WebSocket 경로(배우자)와 셀프 경로(현재 사용자) 각각 다른 트리거. 둘 다 동시 발화 위험 없음 (셀프는 authorId 스킵으로 WS 안 받음).
- **설계 결정**:
  - `sync_event_handler` 의 `_refreshTransactions()` 는 `DateTime.now()` 의 year/month 사용 → 사용자가 과거 월을 보고 있어도 현재월로 갱신되는 이슈는 있으나, 기존 `_refreshTransfers/Dashboard` 도 동일 패턴이라 **이번 범위 밖**.
  - `card_settlement_page` 에서는 **`_selectedYear/_selectedMonth` 를 사용** (결제 처리한 월) — 이 화면은 과거 월 결제도 허용하기 때문.

## 하네스 Scope Audit 결과 (Step 1.5)

하네스 분석 결과 (이 회차 req-1776416585120-015):
- 자동 생성 기획서(4368자)는 **키워드 매칭** 기반 얕은 분석이었음 (무관 파일 포함)
- 탐색 에이전트 재실행으로 **정확한 원인** 재분석 (WebSocket sync 경로 + 셀프 경로 이중 누락)
- 관련 재발 패턴: `filter_propagation` / `navigation_state` — BLoC 동기화 누락은 이 프로젝트 Phase 20-F(b49d080) 에서 **MonthCubit 중앙화** 로 월 변경 경로만 해결되었고, 이벤트 기반(카드결제, 삭제 등)은 case-by-case 로 남아있음.
- **재발 방지**: 신규 `SyncEvent.entityType` 추가 시 `sync_event_handler` 의 모든 영향 BLoC(직접 + 간접) 을 명시적으로 매핑하는 체크리스트. 이번 fix 는 TRANSFER 에 Transaction 이 간접 영향이라는 케이스.
